# Phase 6 — 🏦 코어뱅킹 프로젝트 (4주)

## 목표
지금까지 배운 것으로 **미니 코어뱅킹 시스템**을 처음부터 설계·구현한다.
기능 개수보다 **정합성(돈이 생기거나 사라지지 않음)** 과 **설명 가능한 설계**가 평가 기준이다.

## 도메인 개요

```
고객(Customer) ─< 계좌(Account) >─ 상품(Product: 입출금/정기예금/적금)
                     │
                     ├─< 거래(Transaction)          : 고객이 보는 거래내역
                     └─< 분개(JournalEntry) ─< 분개라인(JournalLine)  : 복식부기 원장
```

### 복식부기(Double-entry) 원장
모든 거래는 **차변(debit) 합계 = 대변(credit) 합계**인 분개로 기록된다.

| 거래 | 차변 | 대변 |
|---|---|---|
| 고객 A가 현금 10,000원 입금 | 현금(자산) 10,000 | 고객예금 A(부채) 10,000 |
| A → B 3,000원 이체 | 고객예금 A 3,000 | 고객예금 B 3,000 |
| 이자 100원 지급 | 이자비용 100 | 고객예금 A 100 |

→ 시스템 어디선가 버그가 나도 "차변 ≠ 대변"으로 **즉시 탐지**할 수 있다. 은행 원장의 핵심 안전장치.

## 주차별 미션 (상세 문서는 Phase 5 완료 후 작성)

### 1주 — 도메인 모델링
- 요구사항 정의서 직접 작성 (유스케이스, 업무 규칙, 예외 상황)
- ERD 설계, 계좌 상태 머신(개설/정상/정지/휴면/해지), 계정과목 설계
- 복식부기 분개 엔진: 불균형 분개는 생성 자체가 불가능하도록

### 2주 — 입출금/이체
- 입금/출금/당행이체 API, 거래 + 분개 동시 기록(한 트랜잭션)
- **멱등성**: `Idempotency-Key`를 DB 유니크 제약으로 보장, 처리 중(IN_PROGRESS) 상태 처리
- 1회/1일 이체 한도, 비밀번호 오류 5회 시 정지
- 동시성 테스트: 핫 계좌(인기 계좌)에 1,000 동시 입금, 랜덤 이체 1만 건 후 총액/원장 균형 검증

### 3주 — 배치 & 대사
- Spring Batch로 일일 이자 계산·지급 배치 (청크 처리, 재시작 가능성, 중복 지급 방지)
- 일 마감: 계좌별 잔액 스냅샷, **원장 합계 vs 계좌 잔액 대사(reconciliation)** 배치, 불일치 리포트
- 정기예금 만기 해지 처리

### 4주 — 외부 연동 & 확장
- 타행이체 시뮬레이션: 가짜 "금융결제원" 서버(지연·실패·타임아웃 랜덤) 연동
  - 타임아웃 시 결과 불명확(Unknown) 상태 → 조회 API로 확인 → 보상 처리
  - 재시도 + 지수 백오프, 서킷 브레이커(Resilience4j)
- 서버 2대 띄우기 → Redis 분산락(Redisson)이 필요한 지점 찾기, DB 락과 비교
- k6로 이체 API 부하 테스트, 병목 분석
