# M6-4 이체 한도, 비밀번호 오류 정지, 동시성 검증

> 가이드 수준: L3, 예상 시간: 5~7h, 선행: M6-3

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 남은 1일 한도보다 큰 금액의 이체가 동시에 10건 들어와도 한도를 넘는 이체가 0건인 것을 통합 테스트로 보여준다.
- Asia/Seoul 기준 23:59:59.999와 00:00:00.000에 같은 이체를 보내 1일 누적 한도가 자정에 초기화되는 것을 `Clock` 교체 테스트로 보여준다.
- 비밀번호 오류 횟수가 요청 실패(롤백)와 상관없이 저장되고, 연속 5회째에 계좌가 `SUSPENDED`가 되는 것을 테스트로 보여준다.
- 핫 계좌 동시 입금 1,000건과 랜덤 이체 10,000건 후 INV-1, INV-2와 이 문서의 불변식 L1~L3이 성립하는 것을 테스트와 측정표로 보여준다.

## 배경
계정 탈취나 오입력 사고에서 피해 금액의 상한을 정하는 것이 이체 한도다. 한도 검사가 "누적액 조회 → 비교 → 이체"로 나뉘어 있으면, 동시에 들어온 이체 여러 건이 모두 같은 누적액을 읽고 통과한다. Phase 2 M2-1에서 본 lost update가 한도라는 이름으로 다시 나타난다.
비밀번호 오류 횟수는 반대 방향의 함정이 있다. 오류 응답을 보내면서 트랜잭션을 롤백하면 증가시킨 횟수도 함께 롤백되어, 공격자는 무한히 비밀번호를 시도할 수 있다.
M6-3에서 만든 이체 API에 두 규칙을 더하고, 지금까지 만든 기능 전체를 동시성 부하 아래에서 검증한다.

## 요구사항

### 1. 이체 한도 (`lab.corebank.limit`)
아래 금액과 범위는 **이 미션의 규칙**이다(실제 은행 한도는 은행, 인증수단마다 다르다).

1. 계좌 개설 시 `transfer_limit` 행을 1회 한도 1,000,000원, 1일 한도 5,000,000원으로 만든다.
2. 한도는 이체 출금(당행이체, M6-7의 타행이체)에만 적용한다. 현금 출금에는 적용하지 않는다.
3. 1회 한도: 이체 금액 ≤ 1회 한도면 통과. 1,000,000원은 통과, 1,000,001원은 422 `PER_TRANSACTION_LIMIT_EXCEEDED`.
4. 1일 한도: (해당 업무일자의 출금계좌 이체 누적액 + 이번 금액) ≤ 1일 한도면 통과. 아니면 422 `DAILY_LIMIT_EXCEEDED`. 누적액 4,000,000원에서 1,000,000원은 통과(누적 5,000,000), 그 뒤 1원은 거부.
5. 업무일자는 `Clock`(zone `Asia/Seoul`)의 현재 시각으로 구한 `LocalDate`다. 누적액은 업무일자마다 따로 쌓이고, 새 업무일자의 첫 이체가 누적액 0에서 시작한다(자정 초기화 배치를 따로 돌리지 않는다).
6. 누적액은 `daily_transfer_usage`(Flyway `V4__`, (`account_id`, `usage_date`) 유니크) 같은 테이블에 이체 성공과 같은 트랜잭션으로 반영한다. 거절된 이체는 누적액에 들어가지 않는다.
7. M6-7에서 `FAILED`로 확정되어 보상된 타행이체 금액은 원래 업무일자의 누적액에서 뺀다(이 미션의 규칙).
8. 한도 변경 API는 만들지 않는다. 테스트는 `transfer_limit` 행을 직접 바꿔 준비한다.

### 2. 계좌 비밀번호와 오류 정지
1. 계좌 개설 요청에 `password`(숫자 4자리 문자열, 이 미션의 규칙)를 추가한다. 숫자 4자리가 아니면 400. 저장은 `spring-security-crypto`의 `BCryptPasswordEncoder` 해시로만 한다.
2. 현금 출금과 이체 출금 요청 본문에 `password`가 필수다.
3. 비밀번호가 틀리면 422 `PASSWORD_MISMATCH`, 응답 본문에 남은 시도 횟수 `remainingAttempts`(5 − 연속 오류 횟수)를 넣는다.
4. 연속 오류 횟수가 5가 되는 요청은(5회는 이 미션의 규칙이다. 실제 오류 허용 횟수는 은행, 인증수단마다 다르다) 422 `PASSWORD_LOCKED`로 응답하고, 계좌를 M6-1의 전이 T1(`ACTIVE` → `SUSPENDED`, 사유 `PASSWORD_LOCKED`)로 바꾼다. 이후 요청은 비밀번호가 맞아도 422 `ACCOUNT_STATUS_NOT_ALLOWED`다.
5. 비밀번호가 맞으면 연속 오류 횟수를 0으로 만든다. 관리자 해제(T3)도 0으로 만든다. 관리자 해제는 `POST /api/admin/accounts/{accountNumber}/resume`로 만들고, 이 Phase에서는 관리자 인증을 하지 않는다(이 미션의 규칙).
6. 오류 횟수 증가와 T1 전이는 요청이 422로 끝나도 커밋되어 있어야 한다.
7. 같은 계좌에 틀린 비밀번호 요청 8개가 동시에 와도 연속 오류 횟수는 5를 넘지 않고, `account_status_history`의 `PASSWORD_LOCKED` 행은 1개다.
8. M6-3의 요청 해시 정규화에서 `password` 필드를 뺀다. 4자리 비밀번호가 들어간 문자열의 SHA-256은 10,000번 시도로 역산된다.

### 3. 검사 순서
여러 규칙을 동시에 어긴 요청은 아래 순서에서 처음 걸린 에러 코드 하나만 돌려준다(이 미션의 규칙): 형식 검증(400) → 멱등 판단 → 계좌 존재, 소유(404) → 계좌 상태 → 비밀번호 → 1회 한도 → 1일 한도 → 잔액.

### 4. 동시성 통합 테스트 (Testcontainers MySQL 8.4)
1. 핫 계좌 입금: 잔액 0원 계좌 H에 1,000원 현금 입금 요청 1,000건을 스레드 100개 풀로 동시에 보낸다(요청마다 다른 멱등 키).
2. 랜덤 이체: 계좌 100개를 각 1,000,000원으로 준비하고, 시드 `20261110`의 `java.util.Random`으로 출금계좌, 입금계좌(서로 다름), 금액(1~50,000원 정수, 균등)을 뽑은 당행이체 10,000건을 스레드 32개로 보낸다. 비밀번호는 모두 맞게 보낸다.
3. 데드락이나 락 대기 타임아웃이 나면 같은 요청을 최대 3번 재시도할 수 있다. 3번 모두 실패하면 테스트 실패로 본다.

랜덤 이체가 끝난 뒤 성립해야 하는 불변식:
- INV-1, INV-2
- L1: Σ(계좌 100개 잔액) == 100,000,000원
- L2: 모든 계좌 잔액 ≥ 0원
- L3: 계좌마다 `daily_transfer_usage.used_amount` == 그 계좌의 그날 성공한 `TRANSFER_OUT` 금액 합계 ≤ 5,000,000원
- L4: 성공 수 + 422 응답 수 == 10,000, 422의 에러 코드는 `INSUFFICIENT_BALANCE`, `DAILY_LIMIT_EXCEEDED` 두 가지뿐, 5xx 응답 0건
- L5: `account_transaction` 행 수 == 성공 수 × 2

### 5. 측정 문서 `workspace/docs/concurrency-report.md`
- 표 위에 JDK 버전, CPU 코어 수, OS, MySQL 컨테이너 메모리 제한, HikariCP `maximum-pool-size`를 적는다.
- 랜덤 이체 테스트를 워밍업 3회 후 5회 측정하고 중앙값 행을 추가한다. 열: `실행 | 소요 시간(ms) | 성공 수 | INSUFFICIENT_BALANCE | DAILY_LIMIT_EXCEEDED | 재시도 횟수 | 데드락 발생 수`.
- 데드락이 1번이라도 났다면 `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK` 부분을 붙이고, 두 트랜잭션이 어떤 순서로 어떤 행을 잠갔는지 적는다.

## 직접 작성할 테스트 시나리오
`workspace/docs/test-scenarios/M6-4.md`에 표(번호 / Given / When / Then)를 쓰고 리뷰를 받은 뒤 구현한다. 시각은 `2026-11-10T23:59:59.999+09:00`처럼 오프셋까지 적는다.

반드시 포함할 경우 (최소 18개 행):
1. 1회 한도 경계: 999,999원 / 1,000,000원 / 1,000,001원
2. 1일 한도 경계: 누적 4,000,000원에서 1,000,000원(성공) 후 1원(거부)
3. 한도 초과와 잔액 부족을 동시에 어긴 요청의 에러 코드(3절 순서)
4. 현금 출금 1,500,000원은 1회 한도와 상관없이 성공하는 경우
5. 자정 경계: 누적 5,000,000원 상태에서 `23:59:59.999+09:00`에 1원(거부), `00:00:00.000+09:00`에 1,000,000원(성공)
6. UTC 기준으로는 같은 날짜지만 Asia/Seoul로는 다른 날짜인 시각 2개(`2026-11-10T14:59:59Z`, `2026-11-10T15:00:00Z`)의 누적액이 다른 업무일자에 쌓이는 경우
7. 누적 4,000,000원에서 600,000원 이체 2건 동시: 성공 1, `DAILY_LIMIT_EXCEEDED` 1, 누적 4,600,000원 (1,500,000원처럼 1회 한도를 넘는 금액은 1일 한도 검사 전에 `PER_TRANSACTION_LIMIT_EXCEEDED`로 거부되므로 쓰지 않는다)
8. 누적 0원에서 600,000원 이체 10건 동시: 성공 8, 거부 2, 누적 4,800,000원
9. 비밀번호 4회 오류 후 정답: 성공, 횟수 0
10. 5회 연속 오류: 5번째 응답 `PASSWORD_LOCKED`, 상태 `SUSPENDED`, 이력 1행
11. 정지 후 맞는 비밀번호로 출금: `ACCOUNT_STATUS_NOT_ALLOWED`
12. 관리자 해제 후 오류 1회: `remainingAttempts` 4
13. 틀린 비밀번호 동시 8건: 횟수 5, 이력 `PASSWORD_LOCKED` 1행
14. 비밀번호 `"123"`, `"12345"`, `"12a4"`로 계좌 개설: 400
15. 핫 계좌 동시 입금 1,000건: 잔액 1,000,000원, 분개 1,000개, 거래내역 1,000행
16. 랜덤 이체 10,000건 후 4절의 불변식 전부

## 제약
- 1일 누적액을 JVM 메모리(`AtomicLong`, `ConcurrentHashMap`)에 두지 않는다: 재시작하면 0이 되고, M6-8의 인스턴스 2대에서 한도가 2배가 된다.
- 비밀번호 원문, 해시, 오류 횟수를 로그에 남기지 않는다.
- 날짜 계산에 `LocalDate.now()`, `new Date()`, `System.currentTimeMillis()`를 직접 쓰지 않는다. 모두 주입받은 `Clock`에서 구한다.
- 동시성 테스트에서 `@Transactional`을 테스트 메서드에 붙이지 않는다: 테스트 트랜잭션이 롤백되면 다른 스레드가 커밋 결과를 볼 수 없다.
