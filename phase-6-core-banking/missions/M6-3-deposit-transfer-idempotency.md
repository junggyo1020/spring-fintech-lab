# M6-3 입출금, 당행이체와 멱등성

> 가이드 수준: L3, 예상 시간: 6~8h, 선행: M6-2

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 입금, 출금, 당행이체 1건이 `account.balance` 변경, `account_transaction` 행, 균형 잡힌 분개를 한 DB 트랜잭션으로 남기고, 중간 실패 시 셋 다 남지 않는 것을 통합 테스트로 보여준다.
- 같은 `Idempotency-Key` 이체 요청을 순차로 10번, 동시에 20개 스레드로 보내도 분개가 1개만 생기는 것을 통합 테스트로 보여준다.
- 처리 도중 프로세스가 죽어 `IN_PROGRESS`로 남은 멱등 레코드를 30초 뒤 재요청이 이어받되, 원래 요청이 늦게 끝나도 돈이 두 번 움직이지 않는 것을 테스트로 보여준다.

## 배경
이체 API의 응답이 네트워크에서 유실되면 클라이언트는 같은 요청을 다시 보낸다. 서버가 첫 요청을 이미 처리했다면 고객은 같은 이체를 두 번 하게 된다. 반대로 서버가 "중복 같으니 무시"를 메모리에서 판단하면 재시작이나 인스턴스 추가 후 판단 근거가 사라진다.
또 잔액만 바뀌고 분개나 거래내역이 남지 않으면, 고객 화면과 원장이 서로 다른 이야기를 한다.
Phase 4 M4-4에서 `Idempotency-Key`를 메모리로 처리했다. M6-2의 분개 엔진 위에서, 이번에는 DB 유니크 제약으로 멱등성을 보장한다.

## 요구사항

### 1. API (`lab.corebank.transfer`, `lab.corebank.account`)
모든 요청은 `X-Customer-Id` 헤더가 필요하다(없으면 400). 금액은 JSON 문자열(예: `"10000"`)로 주고받는다(Phase 4 M4-6 규칙). 에러 응답은 `ProblemDetail`이고 `code` 속성에 에러 코드를 담는다.

| 메서드 | 경로 | 멱등 키 | 성공 응답 |
|---|---|---|---|
| POST | `/api/customers` | 필요 없음 | 201 + 고객 ID |
| POST | `/api/accounts` | 필수 | 201 + 계좌번호, 상태 `ACTIVE`, 잔액 `"0"` |
| GET | `/api/accounts/{accountNumber}` | - | 200 + 잔액, 상태 |
| POST | `/api/accounts/{accountNumber}/deposits` | 필수 | 200 + 거래 ID, 거래 후 잔액 |
| POST | `/api/accounts/{accountNumber}/withdrawals` | 필수 | 200 + 거래 ID, 거래 후 잔액 |
| POST | `/api/transfers` | 필수 | 200 + 이체 ID, 출금계좌 거래 후 잔액 |
| GET | `/api/accounts/{accountNumber}/transactions` | - | 200 + 최신순 거래내역 (페이지 크기 20 고정, 커서 방식은 M4-5와 같게) |

- 다른 고객의 계좌에서 출금, 이체 출금을 요청하면 404 `ACCOUNT_NOT_FOUND`로 응답한다(계좌 존재 여부를 노출하지 않는다, 이 미션의 규칙). 이체의 입금계좌는 다른 고객 계좌여도 된다.
- 현금 입금 분개: 차변 현금 / 대변 고객예금. 현금 출금 분개: 차변 고객예금 / 대변 현금. 당행이체 분개: 차변 고객예금(출금계좌) / 대변 고객예금(입금계좌).
- 당행이체 1건은 `account_transaction` 행 2개(출금계좌 `TRANSFER_OUT`, 입금계좌 `TRANSFER_IN`)와 분개 1개를 만든다.
- M6-1의 금액 규칙(`BR-`)과 상태별 허용 거래 표를 그대로 적용한다.

### 2. 한 트랜잭션 규칙
1. 잔액 변경, `account_transaction` INSERT, 분개 저장, 멱등 레코드 `COMPLETED` 갱신은 **하나의 DB 트랜잭션**에서 커밋된다.
2. 출금계좌 잔액 동시 수정은 M5-8의 3가지 방법(비관적 락 / 낙관적 락 + 재시도 / 조건부 UPDATE) 중 하나로 막는다. 무엇을 골랐고 왜인지 `idempotency-design.md`의 "동시성 전략" 절에 적는다.
3. 당행이체가 계좌 2개를 잠근다면 계좌 ID가 작은 쪽부터 잠근다: M5-9에서 재현한 A→B / B→A 데드락을 막기 위해서다.

### 3. 멱등 처리 규칙 (`lab.corebank.idempotency`)
아래는 **이 미션의 규칙**이다. IETF 초안(draft-ietf-httpapi-idempotency-key-header)의 상태 코드 제안(409, 422)을 따랐지만, 보관 기간, 이어받기 시간은 이 레포에서 정한 값이다.

1. 키 형식: 1~64자, 영문 대소문자, 숫자, 하이픈만. 위반하거나 헤더가 없으면 400 `IDEMPOTENCY_KEY_INVALID`.
2. 유일성 범위: (`customer_id`, `idempotency_key`). 다른 고객이 같은 키를 쓰는 것은 별개 요청이다.
3. 요청 해시: SHA-256(HTTP 메서드 + `"\n"` + 경로 + `"\n"` + 정규화한 본문). 정규화는 본문 필드를 이름 오름차순으로 `이름=값`을 `&`로 이은 문자열이다. JSON 공백, 필드 순서만 다른 요청은 같은 해시가 된다.
4. 상태: `IN_PROGRESS`, `COMPLETED`, `FAILED`.
   - `COMPLETED`: 처리 성공. 응답 상태 코드와 응답 본문을 저장한다.
   - `FAILED`: 업무 규칙 위반(4xx)으로 거절. 응답 상태 코드와 본문을 저장한다. 같은 키 재요청에는 저장된 4xx를 그대로 돌려준다(잔액 부족으로 거절된 키를 나중에 재시도해도 같은 422다).
   - 시스템 오류(DB 연결 실패 등 5xx): 멱등 레코드를 별도 트랜잭션으로 삭제해 같은 키로 재시도할 수 있게 한다. 삭제조차 실패하면(프로세스 종료 포함) 레코드는 `IN_PROGRESS`로 남고 아래 6번 규칙으로 처리한다.
5. 처리 순서:
   - (a) `IN_PROGRESS` 레코드 INSERT를 **별도 짧은 트랜잭션으로 먼저 커밋**한다. 이때 무작위 `owner_token`(UUID)을 함께 저장한다.
   - (b) 유니크 제약 위반이면 기존 레코드를 읽어 판단한다: 해시가 다르면 422 `IDEMPOTENCY_KEY_REUSED` / `COMPLETED`, `FAILED`면 저장된 응답을 그대로 반환하고 응답 헤더 `Idempotent-Replayed: true`를 붙인다 / `IN_PROGRESS`면 409 `IDEMPOTENCY_IN_PROGRESS`와 `Retry-After: 1` 헤더를 즉시 반환한다(기다리지 않는다).
   - (c) 업무 트랜잭션 안에서 마지막에 `status='IN_PROGRESS' AND owner_token=내 토큰` 조건으로 레코드를 `COMPLETED`로 바꾼다. 바뀐 행이 1개가 아니면 업무 트랜잭션 전체를 롤백한다.
6. 오래된 `IN_PROGRESS` 이어받기: `IN_PROGRESS` 레코드의 마지막 갱신 시각이 `Clock` 기준 30초보다 오래됐고 요청 해시가 같으면, 새 요청은 `owner_token`을 새 값으로 바꾸는 조건부 UPDATE(조건: 상태 `IN_PROGRESS`, 갱신 시각 30초 초과, 기존 토큰 일치)로 레코드를 이어받는다. 바뀐 행이 1개면 처리를 진행하고, 0개면 409를 반환한다. 원래 요청이 뒤늦게 5-(c)에 도달하면 토큰이 달라 롤백된다.
7. 보관 기간: 레코드 생성 후 24시간 동안 멱등을 보장한다. 24시간이 지난 레코드를 지우는 배치는 이 미션 범위 밖이다.

### 4. 설계 문서 `workspace/docs/idempotency-design.md`
- 3절 5번 처리 순서를 시퀀스 다이어그램(Mermaid `sequenceDiagram`)으로 그린다: 정상 1회, 동시 중복 2개, 오래된 `IN_PROGRESS` 이어받기 3개 그림.

- 동시성 전략 절 (2절 2번).

9. 같은 키, 다른 금액: 422 `IDEMPOTENCY_KEY_REUSED`
10. 같은 키, 같은 본문, JSON 필드 순서만 다름: 재생 응답

15. 31초 전 `IN_PROGRESS`를 이어받아 처리가 끝난 뒤, 원래 토큰으로 5-(c)를 실행하면 롤백되어 분개가 1개로 유지되는 경우
16. 모든 테스트 종료 시점에 INV-1(모든 분개 균형), INV-2(Σ고객 잔액 == 고객예금 원장 잔액) 검사

## 제약
- 멱등 판단에 `ConcurrentHashMap`, Caffeine 같은 JVM 메모리 저장소를 쓰지 않는다: 인스턴스가 2대가 되면(M6-8) 각자 다른 판단을 한다.
- 멱등 레코드 존재 여부를 SELECT로 먼저 확인한 뒤 INSERT하는 방식("확인 후 삽입")만으로 중복을 막지 않는다. 판단의 최종 근거는 유니크 제약 위반이다: 두 요청이 동시에 SELECT하면 둘 다 "없음"을 본다.
- `Thread.sleep`으로 타이밍을 맞춘 동시성 테스트를 쓰지 않는다. 동시 출발은 `CountDownLatch`, 시간 경과는 `Clock` 교체로 재현한다.
- 컨트롤러에 업무 로직을 두지 않는다(Phase 4 완료 기준과 같다).
