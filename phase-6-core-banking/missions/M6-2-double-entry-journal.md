# M6-2 복식부기 분개 엔진

> 가이드 수준: L3 · 예상 시간: 4~6h · 선행: M6-1

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 차변 합계와 대변 합계가 다른 `JournalEntry`를 만들려는 모든 경로가 예외로 끝나는 것을 단위 테스트로 보여준다.
- README 2절 복식부기 표의 5개 거래를 분개로 기록한 뒤, 계정과목별 잔액과 시산표(Σ차변 == Σ대변)를 조회 쿼리로 보여준다.
- 기록된 분개를 UPDATE·DELETE하려는 시도가 애플리케이션과 DB 양쪽에서 거부되고, 정정은 반대 분개로만 된다는 것을 테스트로 보여준다.

## 배경
계좌 잔액만 저장하는 시스템에서는 잔액이 틀려도 "어디서 틀렸는지" 찾을 근거가 없다. 복식부기는 모든 돈의 움직임을 "어디서 와서 어디로 갔는가" 두 면으로 기록하므로, 한쪽만 기록되는 버그가 Σ차변 ≠ Σ대변으로 바로 드러난다.
원장을 고치거나 지울 수 있으면 이 안전장치는 사라진다. 운영자가 잘못된 분개를 UPDATE로 고치면 감사 시점에 "원래 무엇이 기록됐는지"를 복원할 수 없다.
M6-1에서 `ledger_account`, `journal_entry`, `journal_line` 테이블을 설계했다. 이 미션은 그 테이블에 불균형 분개가 들어갈 수 없게 만드는 도메인 코드다. M6-3부터 모든 입출금·이체는 이 엔진을 거친다.

## 요구사항

### 1. 계정과목 (Flyway `V2__ledger_accounts.sql`로 초기 데이터 입력)
아래 계정 코드와 이름은 **이 레포에서 정한 것**이다(실제 은행 계정과목 체계는 은행마다 다르다). `대외결제예치금`은 M6-7에서 쓰는 이 미션의 규칙 계정이다.

| 코드 | 이름 | 유형 | 정상 잔액 방향 |
|---|---|---|---|
| 1010 | 현금 | 자산 | 차변 |
| 1020 | 대외결제예치금 | 자산 | 차변 |
| 2010 | 고객예금 | 부채 | 대변 |
| 2110 | 예수소득세 | 부채 | 대변 |
| 2120 | 예수지방소득세 | 부채 | 대변 |
| 2210 | 타행이체미정산 | 부채 | 대변 |
| 5010 | 이자비용 | 비용 | 차변 |

계정 잔액 = 정상 잔액 방향이 차변이면 Σ차변 − Σ대변, 대변이면 Σ대변 − Σ차변.

### 2. 도메인 객체 (`lab.corebank.ledger`)
1. `JournalEntry`(분개)와 `JournalLine`(분개 라인)을 만든다. `JournalEntry`는 정적 팩터리 메서드 또는 빌더의 `build()`로만 만들 수 있고, 그 안에서 아래 불변식을 모두 검사한다. 하나라도 어기면 `UnbalancedJournalEntryException` 또는 `InvalidJournalEntryException`(학습자가 이름을 정해도 되지만 둘을 구분한다)을 던지고 객체는 만들어지지 않는다.
   - J1: 라인이 2개 이상이다.
   - J2: 차변 라인과 대변 라인이 각각 1개 이상이다.
   - J3: 모든 라인 금액은 1원 이상의 원화 정수다(0원, 음수, 소수 금지).
   - J4: Σ차변 금액 == Σ대변 금액. 어기면 `UnbalancedJournalEntryException`, 메시지에 두 합계를 모두 적는다.
   - J5: 계정과목이 `고객예금`(2010)인 라인은 고객 계좌 ID가 반드시 있고, 다른 계정과목 라인은 고객 계좌 ID가 없다.
   - J6: 업무일자와 분개 유형이 null이 아니다.
2. 만들어진 `JournalEntry`는 불변이다. 라인 목록을 돌려주는 메서드는 수정할 수 없는 목록을 돌려주고, setter가 없다.
3. 분개 유형(이 미션의 규칙): `DEPOSIT`, `WITHDRAWAL`, `TRANSFER`, `INTEREST`, `INTERBANK_REQUEST`, `INTERBANK_SETTLE`, `INTERBANK_COMPENSATE`, `REVERSAL`.

### 3. 반대 분개
1. `reverse(원분개, 업무일자)` 기능은 원분개의 모든 라인을 차변↔대변만 바꾸고 금액·계정과목·고객 계좌는 그대로 둔 새 분개를 만든다. 분개 유형은 `REVERSAL`, `reversal_of_entry_id`는 원분개 ID다.
2. 한 분개는 최대 1번만 반대 분개할 수 있다. 두 번째 시도는 `AlreadyReversedException`으로 거부한다(`reversal_of_entry_id` 유니크 제약도 같은 것을 막는다).
3. `REVERSAL` 유형 분개를 다시 반대 분개하는 것은 거부한다(이 미션의 규칙). 잘못된 반대 분개는 새 정상 분개로 바로잡는다.
4. 반대 분개를 기록하면 원분개와 합친 각 계정 잔액 변화가 0이 된다.

### 4. 저장과 불변성
1. `JournalService.post(JournalEntry)`(이름은 바꿔도 된다)는 분개와 라인을 한 DB 트랜잭션에서 저장한다. 라인 저장 중 하나라도 실패하면 분개도 저장되지 않는다.
2. 저장 직전에도 J4를 한 번 더 검사한다. 도메인 객체를 거치지 않고 만들어진 데이터(리플렉션, 잘못된 매핑)를 막기 위해서다.
3. `journal_entry`, `journal_line`에 대한 UPDATE와 DELETE를 막는 MySQL 트리거를 Flyway `V3__journal_immutable_triggers.sql`로 만든다. 트리거는 `SIGNAL SQLSTATE '45000'`으로 오류를 낸다. 트리거 본문을 `SIGNAL` 문 하나로 쓰면 `BEGIN ... END`와 `DELIMITER`가 필요 없다. 테스트 사이의 데이터 정리는 `TRUNCATE TABLE`로 한다. MySQL에서 `TRUNCATE TABLE`은 DELETE 트리거를 실행하지 않는다(외래 키가 걸린 테이블은 `SET FOREIGN_KEY_CHECKS = 0` 후 실행).
4. JPA 엔티티로 매핑한다면 Hibernate 7의 `org.hibernate.annotations.Immutable`을 검토하고, 쓰지 않는다면 이유를 `ledger-design.md`에 적는다.

### 5. 조회
1. 계정과목별 잔액: 입력 계정 코드(고객예금이면 고객 계좌 ID 선택), 출력 정상 잔액 방향 기준 잔액.
2. 시산표: 전체 `journal_line`의 Σ차변, Σ대변, 둘의 차이. 정상 상태에서 차이는 0이다.
3. 두 조회 모두 SQL 집계 1번으로 계산한다(분개를 전부 메모리에 올려서 더하지 않는다).

### 6. 설계 문서 `workspace/docs/ledger-design.md`
- 불변식 J1~J6을 어디서(팩터리, 서비스, DB 제약, 트리거) 검사하는지 표로 적는다.
- 고객예금을 계정과목 1개 + 라인의 고객 계좌 ID로 나눈 방식(보조원장)과, 고객마다 계정과목을 만드는 방식을 비교한 표(행 수 증가, 대사 쿼리, 계정과목 관리)를 적는다.

## 제약
- 금액에 `double`, `float`, `long` 나눗셈을 쓰지 않는다. 금액 연산은 `BigDecimal` 또는 이를 감싼 `Money`로 한다 — 2진 부동소수점 오차와 정수 나눗셈 절사를 막기 위해서다.
- `journal_entry`, `journal_line`에 대한 UPDATE·DELETE 쿼리를 애플리케이션 코드 어디에도 두지 않는다. Spring Data 리포지토리를 쓰면 `delete*` 메서드가 노출되지 않게 `Repository` 인터페이스를 직접 상속해 필요한 메서드만 선언한다.
- 분개 저장과 계좌 잔액 변경을 이 미션에서 연결하지 않는다. 연결은 M6-3에서 한다.
