# Phase 7 — 📈 증권 매매 프로젝트 (4주)

## 목표
주문 접수 → 예수금/잔고 홀드 → **매칭 엔진** → 체결 → 정산 반영까지의 흐름을 구현한다.
코어뱅킹이 "정합성"의 문제였다면, 증권 매매는 **정합성 + 순서 + 지연시간**의 문제다.

## 도메인 개요

```
고객 ─ 증권계좌 ─┬─ 예수금(Cash): 총액 / 주문가능금액 / 홀드금액
                └─ 보유종목(Position): 수량 / 매도가능수량 / 평균단가

주문(Order): 매수/매도, 지정가/시장가, 상태 머신
  접수 → (부분체결) → 체결완료
       → 정정 / 취소 / 거부

호가창(OrderBook): 종목별 매수 호가(높은 가격 우선) / 매도 호가(낮은 가격 우선)
체결(Execution): 매수주문 ↔ 매도주문, 가격, 수량
```

### 핵심 규칙
- **가격-시간 우선 원칙**: 좋은 가격 먼저, 같은 가격이면 먼저 들어온 주문 먼저
- **호가 단위**: 가격대별 최소 가격 단위 (예: 2,000원 미만 1원, ... 실제 KRX 호가 단위표 참고)
- **매수 주문 시 예수금 홀드**: 주문금액 + 예상 수수료만큼 주문가능금액에서 차감, 체결/취소 시 해제
- **매도 주문 시 수량 홀드**: 매도가능수량에서 차감
- 시장가 주문은 반대편 호가를 소진하며 체결, 잔량 처리 정책 결정

## 주차별 미션 (상세 문서는 Phase 6 완료 후 작성)

### 1주 — 도메인 & 주문 접수
- 주문 상태 머신, 호가 단위 검증, 예수금/수량 홀드 (동시 주문에도 초과 주문 불가)
- 주문 접수 API, 주문 거부 사유 체계

### 2주 — 매칭 엔진
- 순수 Java 호가창: `TreeMap<Price, Deque<Order>>` (매수는 역순)
- 지정가/시장가 매칭, 부분 체결, 체결 이벤트 생성
- **단일 스레드 매칭 엔진**: 종목별 이벤트 루프(큐 + 전용 스레드) — 왜 락 대신 단일 스레드인가? (LMAX Disruptor 아키텍처 조사)
- 매칭 엔진 단위 테스트: 시나리오 테이블 기반 수십 개 케이스

### 3주 — 정정/취소 & 체결 반영
- 정정(가격/수량)/취소: 매칭 엔진 큐를 통해서만 처리 (체결과 취소의 경합)
- 체결 → 예수금/보유종목/평균단가 반영, 수수료·거래세 계산
- 체결 이벤트 → 비동기로 계좌 반영 (순서 보장, 멱등 처리)

### 4주 — 실시간 & 복구 & 부하
- WebSocket(STOMP)으로 호가/체결 실시간 브로드캐스트
- **이벤트 소싱**: 주문 이벤트 로그로부터 호가창 재구성 → 엔진 재시작 후 동일 상태 복구 테스트
- 초당 수만 건 주문 부하 테스트, 지연시간 분포(p50/p99) 측정, 병목 개선

## 완료 기준
- [ ] 동시 주문에도 예수금/매도가능수량을 초과하는 주문이 절대 접수되지 않는다
- [ ] 같은 주문 시퀀스를 재생하면 항상 같은 체결 결과가 나온다 (결정성)
- [ ] 체결 수량 합계 = 매수 체결 수량 = 매도 체결 수량, 예수금/수량 홀드 누수 없음
- [ ] 매칭 엔진 설계 문서 (왜 단일 스레드인가, 장애 시 복구 방법)
