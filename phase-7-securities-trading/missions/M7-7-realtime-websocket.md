# M7-7 실시간 시세 WebSocket

> 가이드 수준: L3, 예상 시간: 4~5h, 선행: M7-4

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 종목별 상위 5단계 호가와 체결을 STOMP 토픽으로 브로드캐스트하고, 테스트 안의 `WebSocketStompClient`로 수신 내용을 검증한다
- 호가 스냅샷을 종목당 초당 최대 10회로 제한하고, 주문이 2초 동안 계속 들어올 때 받은 스냅샷 수가 21회 이하라는 것을 테스트로 보여준다
- 체결 메시지가 체결 ID 순서대로 빠짐없이 도착한다는 것을 테스트로 보여준다

## 배경
시세 화면은 고객이 주문 가격을 정하는 근거다. 호가 메시지에 서로 다른 시점의 매수, 매도 레벨이 섞여 있으면 화면에 최우선 매수호가 ≥ 최우선 매도호가인 교차 호가가 보이고, 고객은 체결될 수 없는 가격에 주문을 낸다.
호가가 바뀔 때마다 전부 보내면 주문이 초당 5,000건 들어오는 종목 하나가 초당 최대 5,000개의 호가 메시지를 만들고, 느린 클라이언트의 전송 버퍼가 차서 서버 메모리가 늘어난다.
M7-4에서 엔진 상태는 엔진 스레드만 소유한다고 정했다. 이 미션은 그 규칙을 지키면서 엔진 밖으로 호가 상태를 내보내는 방법을 정한다.

## 요구사항
1. **의존성**: `org.springframework.boot:spring-boot-starter-websocket` (Spring Boot 4.1.2에 있음을 2026-11-10 Maven Central에서 확인). 테스트는 같은 스타터에 포함된 Spring Framework 7의 `WebSocketStompClient`를 쓴다.
2. **STOMP 설정**: 엔드포인트 `/ws`(SockJS 없음), 단순 브로커 접두사 `/topic`. 서버가 보내기만 하고 클라이언트 → 서버 메시지 매핑(`@MessageMapping`)은 만들지 않는다.
3. **토픽과 메시지** (JSON, 가격, 금액은 Phase 4 M4-6 규칙대로 문자열, 수량은 숫자)
   - `/topic/orderbook.{종목코드}`: `symbol`, `sequence`(이 스냅샷이 반영한 마지막 엔진 시퀀스), `bids`, `asks`. 각 배열은 최우선 호가부터 최대 5개, 원소는 `price`, `quantity`(레벨 잔량 합), `orderCount`. 레벨이 5개 미만이면 있는 만큼만 보낸다.
   - `/topic/trades.{종목코드}`: `symbol`, `executionId`, `price`, `quantity`, `aggressorSide`, `sequence`, `executedAt`(접수 시각, ISO-8601 `+09:00`).
4. **스냅샷 일관성**: 호가 스냅샷은 엔진 스레드에서 만든다. 다른 스레드가 `OrderBook`을 직접 읽지 않는다(M7-4 제약). 두 방법 중 하나를 골라 `docs/engine-design.md`의 "시세 스냅샷" 절에 이유를 쓴다.
   - (가) 엔진 스레드가 호가창을 바꾼 명령마다 불변 스냅샷 객체를 만들어 `AtomicReference`에 넣는다.
   - (나) 발행 스케줄러가 스냅샷 조회 명령을 종목 큐에 넣고, 엔진 스레드가 그 명령을 처리할 때 스냅샷을 만든다. 조회 명령은 시퀀스 번호를 받지 않고 M7-8 명령 로그에도 남기지 않는다.
5. **스로틀** (이 미션의 규칙): 종목마다 100ms 간격 고정 주기로 최신 스냅샷의 `sequence`가 마지막으로 보낸 값보다 크면 보내고, 같으면 보내지 않는다. 결과적으로 종목당 초당 최대 10회다. 호가창이 바뀌지 않으면 메시지가 없다.
6. **체결 메시지**: 스로틀 없이 체결 1건마다 1개를 보낸다. 보내는 쪽은 M7-4 사건 출력 큐의 소비 경로에 붙이고 엔진 스레드에서 직접 보내지 않는다. 같은 종목의 체결 메시지는 `executionId` 오름차순으로 보낸다.
7. **메시지 변환**: Spring Framework 7에서 Jackson 3 기반 STOMP 변환기는 `JacksonJsonMessageConverter`(since 7.0)다. Jackson 2 기반 `MappingJackson2MessageConverter`는 7.x에서 제거 예정(deprecated for removal)이므로 쓰지 않는다. 테스트 클라이언트에도 같은 변환기를 설정한다.

## 직접 작성할 테스트 시나리오
`docs/test-scenarios/M7-7.md`에 표를 쓰고 리뷰를 받은 뒤 구현한다. **최소 8개**. 테스트는 `@SpringBootTest(webEnvironment = RANDOM_PORT)`와 `WebSocketStompClient`(`StandardWebSocketClient`)로 실제 연결해서 받는다. 반드시 포함할 경우:

1. M7-3 참조 시나리오 R10의 준비 주문 3개를 넣은 뒤 받은 스냅샷: `bids` = [{`"10000"`, 10, 2}, {`"9990"`, 5, 1}], `asks` = []
2. 매수 레벨 7개(9,940~10,000)를 만든 뒤 스냅샷 `bids` 길이 5, 첫 원소 10,000, 마지막 원소 9,960
3. 스로틀: 구독 후 2초 동안 주문을 1ms마다 1건 넣는다(약 2,000건). 그 2초 동안 받은 스냅샷 수 ≤ 21이고 ≥ 10
4. 주문을 멈춘 뒤 500ms 안에 받은 마지막 스냅샷의 `sequence`가 엔진의 마지막 시퀀스와 같고, 레벨 내용이 엔진 조회 결과의 상위 5단계와 같다
5. 호가창이 바뀌지 않는 1초 동안 스냅샷 0개
6. 체결 300건을 만드는 주문을 넣으면 체결 메시지 300개를 받고, `executionId`가 1씩 빠짐없이 증가한다
7. 받은 모든 스냅샷에서 최우선 매수호가 < 최우선 매도호가 (양쪽 모두 있을 때)
8. `A00001`만 구독한 클라이언트는 `A00002` 주문으로 생긴 메시지를 받지 않는다

## 제약
- 스냅샷을 만들기 위해 엔진 스레드 밖에서 `OrderBook`의 맵을 순회하지 않는다: `ConcurrentModificationException` 또는 교차 호가가 생긴다.
- 체결 메시지 전송을 엔진 스레드에서 하지 않는다: 느린 클라이언트가 엔진을 멈추게 한다.
- 테스트에서 메시지 도착을 `Thread.sleep` 후 확인하지 않는다. `BlockingQueue.poll(timeout)` 또는 Awaitility로 기다린다.

## 힌트
힌트 없음. STOMP 설정은 Spring Framework 레퍼런스 "STOMP" 장의 "Enable STOMP" 절과 "STOMP Client" 절을 본다.

## 생각해볼 질문
1. 스냅샷 대신 변경분(delta)만 보내면 메시지 크기는 줄지만, 클라이언트가 메시지 하나를 놓쳤을 때 무엇이 틀어지는가? `sequence` 필드로 어떻게 감지하고 복구하는가?
2. 같은 종목 구독자가 10,000명이고 그중 100명이 느리면, 단순 브로커의 전송 버퍼는 어떻게 되는가? Spring 레퍼런스 STOMP 장의 "Performance" 절(전송 버퍼 크기, 전송 시간 제한)과 연결해 답한다.
3. Phase 8에서 애플리케이션 인스턴스가 2대가 되면, 엔진이 있는 인스턴스에 연결하지 않은 클라이언트는 시세를 어떻게 받는가? "External Broker" 절의 브로커 릴레이와 Kafka를 쓰는 구성을 비교한다.
