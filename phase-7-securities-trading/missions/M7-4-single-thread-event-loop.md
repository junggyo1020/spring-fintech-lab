# M7-4 단일 스레드 이벤트 루프

> 가이드 수준: L3 · 예상 시간: 5~6h · 선행: M7-3

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 종목마다 전용 스레드 1개가 명령 큐에서 명령을 꺼내 M7-3 엔진을 실행하는 `SymbolEngine`을 만들고, 주문 API가 이 큐로만 엔진에 접근하게 한다
- 같은 명령 100만 건으로 "단일 스레드 + 큐" 방식과 "락으로 보호한 공유 엔진" 방식의 처리량과 p50·p99·p99.9 지연시간을 HdrHistogram으로 측정해 표로 비교한다
- 큐가 가득 찼을 때 주문이 `ENGINE_BUSY`로 거부되고 홀드가 원상복구된다는 것을 테스트로 보여준다

## 배경
매칭 엔진의 호가창은 주문 하나를 처리하는 동안 여러 레벨과 여러 주문을 연달아 바꾼다. 여러 스레드가 이 상태를 같이 만지면 락 하나로 전체를 감싸야 하고, 그러면 스레드가 많아도 한 번에 하나만 일하면서 락 경쟁 비용만 늘어난다.
거래소들이 매칭을 단일 스레드로 처리하는 이유가 이것이며, LMAX는 이 구조로 스레드 1개에서 초당 600만 건을 처리했다고 보고했다.
M7-3에서 스레드 안전하지 않은 엔진을 만들었다. 이 미션은 그 엔진을 바꾸지 않고, 전용 스레드와 큐로 감싸 여러 HTTP 요청 스레드가 안전하게 쓸 수 있게 만든다.

## 요구사항
개념은 [README](../README.md) 7절을 먼저 읽는다. 패키지는 `lab.trading.engine.runtime`.

1. **명령**: 엔진에 들어가는 입력은 명령 객체 하나로 표현한다. 이 미션에서는 `PlaceOrder`(M7-3 입력 주문 + 접수 시각)만 만들고, M7-5에서 `CancelOrder`, `AmendOrder`를 추가한다. 접수 시각은 큐에 넣는 쪽이 주입받은 `Clock`에서 읽어 epoch 밀리초(`long`)로 담는다. 엔진은 시계를 읽지 않는다.
2. **`SymbolEngine`** (종목 1개 = 인스턴스 1개 = 스레드 1개)
   - 큐: 용량 10,000인 bounded 큐 (이 미션의 규칙). `ArrayBlockingQueue` 또는 직접 만든 링 버퍼 중 선택한다.
   - 제출: 큐에 넣지 못하면 기다리지 않고 즉시 실패를 돌려준다. 블로킹 `put`을 쓰지 않는다.
   - 엔진 스레드는 명령을 하나 꺼낼 때마다 시퀀스 번호(종목별 1부터 1씩 증가)를 붙이고 M7-3 엔진을 실행한다. 사건에는 이 시퀀스 번호와 명령의 접수 시각을 붙인다.
   - 엔진 스레드 이름은 `engine-{종목코드}` (스레드 덤프에서 찾기 위해).
   - 엔진 스레드에서 DB 접근, HTTP 호출, 파일 I/O(M7-8 명령 로그 제외)를 하지 않는다.
3. **사건 출력**: 엔진 스레드는 사건을 종목별 출력 큐에 넣는다. 출력 큐를 소비하는 스레드는 종목당 1개이고, M7-6에서 계좌 반영을 여기서 한다. 이 미션에서 소비자는 사건을 받아 주문 상태(`orders` 테이블의 체결수량·취소수량·상태)를 갱신하고, `Execution`과 `OrderCancelled`의 수량만큼 M7-2 홀드 해제 연산을 호출한다. 예수금 차감과 결제 예정 내역은 M7-6에서 붙이므로, 이 미션까지는 체결 후 주문가능금액이 실제보다 크게 보인다. 같은 종목의 사건은 시퀀스 순서대로 처리한다.
4. **`EngineRegistry`** (`lab.trading.application` 패키지, Spring 빈): 애플리케이션 시작 시 `instrument` 테이블의 종목마다 `SymbolEngine`을 하나씩 시작하고, 종료 시 큐에 남은 명령을 모두 처리한 뒤 스레드를 멈춘다. 종료 대기 상한은 5초(이 미션의 규칙)이고, 5초가 지나면 남은 명령 수를 로그에 남긴다.
5. **주문 API 연결**: M7-2의 `POST /api/orders`는 홀드 차감 트랜잭션이 커밋된 **뒤** `PlaceOrder`를 제출한다. 제출이 실패하면 홀드를 해제하고 주문을 `REJECTED`(`ENGINE_BUSY`)로 바꾼 뒤 `503`과 `ProblemDetail`(`code=ENGINE_BUSY`)을 응답한다. `RejectReason`에 `ENGINE_BUSY`를 추가한다.
6. **예외 격리**: 엔진 실행 중 예외가 나면 그 명령만 실패로 기록(로그 + 실패 사건)하고 엔진 스레드는 계속 다음 명령을 처리한다. 스레드가 죽어 그 종목 주문이 영원히 큐에 쌓이는 상황을 막기 위해서다.
7. **비교용 락 엔진**: 같은 M7-3 엔진을 `ReentrantLock` 하나로 감싸 여러 스레드가 직접 호출하는 `LockedEngine`을 테스트 소스에만 만든다.
8. **측정** (`@Tag("benchmark")` 테스트, `./gradlew benchmark`로 실행)
   - 입력: 시드 42로 미리 만든 `PlaceOrder` 1,000,000건을 메모리 배열에 둔다. 구성은 M7-3 무작위 시험과 같다(매수·매도 반반, 지정가 90%·시장가 10%, 가격 9,900~10,100 중 10원 단위, 수량 1~100, 계좌 1~20). 측정 시간에 명령 생성 비용을 넣지 않는다. 측정 중 큐가 가득 차 제출이 실패하면 그 명령을 버리지 않고 성공할 때까지 바로 다시 제출한다(바쁜 대기). 모드 A의 "제출 직전 시각"은 첫 제출 시도 직전이다(재제출로 기다린 시간도 지연에 들어간다). 1,000,000건이 모두 처리돼야 1회 측정이다.
   - 지연시간 1건 = 엔진이 그 명령 처리를 끝낸 `System.nanoTime()` − 측정 시작 기준 시각. 기준 시각은 모드별로 아래와 같다. 엔진 스레드에서 `org.hdrhistogram.Histogram`(나노초 단위, 최대 추적값 10초 = 10,000,000,000, 유효숫자 3자리)에 기록한다.
   - 모드 A (최대 처리량): 생산자 스레드 1개가 큐가 허용하는 만큼 계속 넣는다. 기준 시각 = 제출 직전 시각. 처리량 = 1,000,000 ÷ (첫 제출 ~ 마지막 처리 완료 시간).
   - 모드 B (고정 부하 50,000건/초): 생산자가 `i`번째 명령을 `시작 + i × 20µs`에 넣는다(바쁜 대기). 기준 시각 = 예정된 제출 시각 `시작 + i × 20µs`. 생산자가 늦어진 시간까지 지연으로 잡아 coordinated omission을 피하기 위해서다.
   - `LockedEngine`: 생산자 스레드 4개가 각자 250,000건을 직접 호출한다. 모드 A만 측정하고, 지연 1건 = 호출 직전 ~ 반환 시각(락 대기 포함).
   - 측정 규칙: 워밍업 3회 실행 후 5회 측정, 각 지표의 중앙값을 기록한다. 표 위에 JDK 버전, CPU 모델과 코어 수, OS, `-Xmx`를 적는다.
   - 목표 (이 미션의 규칙, 노트북 기준): `SymbolEngine` 모드 A 처리량 200,000건/초 이상, 모드 B p99 1ms 이하. 미달이면 JFR(`-XX:StartFlightRecording`) 결과에서 가장 시간을 많이 쓴 메서드 3개를 보고서에 적는다.
9. **문서**: `docs/latency-report.md`에 아래 표를 채운다. `docs/engine-design.md`에 "단일 스레드를 고른 이유"(측정값 인용), "큐가 가득 찼을 때 동작", "엔진 스레드 예외 시 동작" 절을 쓴다.

## 직접 작성할 테스트 시나리오
`docs/test-scenarios/M7-4.md`에 표를 쓰고 리뷰를 받은 뒤 구현한다. **최소 8개** (측정 테스트 제외). 반드시 포함할 경우:

1. 서로 다른 HTTP 요청 스레드 8개가 같은 종목에 주문 1,000건씩 동시에 제출 → 엔진이 붙인 시퀀스 번호가 1~8,000에서 빠짐·중복 없음, M7-3 불변식 I1~I4가 마지막 상태에서 성립
2. 큐 용량 초과: 엔진 스레드를 테스트용 장치(예: 첫 명령 처리 중 `CountDownLatch` 대기)로 멈춘다. 첫 명령은 큐에서 이미 꺼냈으므로, 이어서 제출한 10,000건이 큐를 채우고 그다음 1건(전체 10,002번째) 제출이 실패한다 → 제출 실패, API 응답 `503`·`code=ENGINE_BUSY`, 그 주문의 홀드 해제, 상태 `REJECTED`
3. 엔진 실행 중 예외를 내는 명령(테스트용으로 주입) 다음에 넣은 정상 명령이 처리된다
4. 종목 2개에 동시에 주문을 넣으면 각 종목 엔진 스레드 이름이 `engine-A00001`, `engine-A00002`로 다르고 서로의 시퀀스에 영향이 없다
5. 같은 명령 목록을 생산자 1개로 5번 넣으면 5번 모두 체결 사건 목록이 같다
6. 종료 시 큐에 남은 명령 500건이 모두 처리된 뒤 스레드가 멈춘다
7. 출력 큐 소비자가 갱신한 `orders` 테이블의 체결수량 합(매수 쪽) = 체결수량 합(매도 쪽) = 엔진 체결 사건 수량 합

## 제약
- 엔진 스레드에서 `synchronized`·`Lock`을 쓰지 않는다 — 단일 스레드가 상태를 소유하므로 필요 없고, 쓰면 비교 측정의 의미가 없어진다.
- 큐에 넣는 쪽이 `OrderBook`을 직접 읽지 않는다 — `TreeMap`은 스레드 안전하지 않아 다른 스레드에서 읽으면 데이터 경쟁이다. 조회가 필요하면 조회 명령을 큐에 넣는다.
- 측정에 JUnit `assertTimeout`을 쓰지 않는다 — 지연 분포가 아니라 단일 시간만 본다.
- LMAX Disruptor 라이브러리(`com.lmax:disruptor`)는 이 미션에서 쓰지 않는다. 읽을거리로만 본다. 직접 만든 큐 구조와 비교하는 질문이 아래에 있다.

## 생각해볼 질문
1. `ArrayBlockingQueue`는 내부에 락을 쓴다. 그런데도 "단일 스레드 엔진은 락이 없다"고 말할 수 있는 이유는 무엇인가? Disruptor 논문 2.1절 "The Cost of Locks"와 2.5절 "The Problems of Queues"를 읽고, 이 미션 큐의 비용이 측정 결과 어디에 나타나는지 답한다.
2. 종목이 3,000개일 때 종목마다 스레드를 1개씩 두면 무엇이 문제인가? 종목을 고정 개수 스레드에 나눠 배정(`종목코드 해시 % 스레드 수`)하면 어떤 종목 조합에서 지연이 늘어나는가?
3. Phase 8에서 엔진을 별도 서비스로 분리하면 "홀드 차감 커밋 후 큐에 제출"이 네트워크 호출이 된다. 커밋은 됐는데 제출 응답이 오지 않으면 주문은 엔진에 들어간 것인가? M8-3의 Outbox가 이 문제를 어떻게 바꾸는가?
