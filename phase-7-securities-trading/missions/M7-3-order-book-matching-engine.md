# M7-3 호가창과 매칭 엔진

> 가이드 수준: L3 · 예상 시간: 8~9h · 선행: M7-1

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 매수는 내림차순, 매도는 오름차순으로 가격 레벨을 정렬하고 레벨 안은 도착 순서(FIFO)로 꺼내는 호가창을 Spring 없이 순수 Java로 만든다
- 참조 시나리오 12개의 체결(가격·수량·상대 주문)과 실행 후 호가창을 한 건도 다르지 않게 재현한다
- 무작위 명령 10,000건을 넣는 동안 매 명령 뒤에 "호가창이 교차하지 않는다" 등 불변식 4개를 검사하는 테스트를 만든다

## 배경
매칭 규칙이 하나라도 모호하면 같은 주문 순서에서 고객마다 다른 체결 결과를 받고, 거래소는 어느 쪽이 맞는지 설명할 수 없다. 체결가격이 1원 달라지면 100주 체결 1건에서 100원이 어긋나고, 고객은 그 차액을 근거로 분쟁을 제기한다.
그래서 이 미션은 L3이지만 매칭 규칙과 기대 결과를 표로 전부 정해 준다. 설계(클래스 구성, 자료구조 선택의 세부)는 직접 한다.
M7-1의 `Order`는 계좌 쪽 주문 기록이다. 이 미션의 엔진은 그 주문을 받아 체결 사건을 만들어 내는 별도 구성요소이며, M7-4에서 전용 스레드에 올라간다.

## 요구사항
개념은 [README](../README.md) 3절을 먼저 읽는다. 패키지는 `lab.trading.engine`이고, Spring·JPA·`java.time`·`lab.trading.application`에 의존하지 않는다.

1. **엔진 입력 주문** (이 미션에서 쓰는 필드): 주문 ID(`long`, 엔진 안에서 유일), 계좌 ID, 매수/매도, 지정가/시장가, 지정가 가격(시장가는 없음), 수량. 가격·호가단위·가격제한폭 검증은 M7-1에서 끝났다고 보고 엔진은 다시 검사하지 않는다. 이미 엔진에 있는 주문 ID가 다시 들어오면 `IllegalArgumentException`을 던지고 호가창은 바뀌지 않는다.
2. **`OrderBook`** (종목 1개)
   - 매수 레벨: 가격 내림차순, 매도 레벨: 가격 오름차순. 레벨 안의 주문은 도착 순서 큐.
   - 수량이 0이 된 주문은 즉시 레벨에서 빠지고, 주문이 없는 레벨은 즉시 맵에서 빠진다.
   - 조회: 최우선 매수호가, 최우선 매도호가, 각 방향의 레벨 목록(가격, 잔량 합계, 주문 수), 특정 레벨의 주문 ID 순서. M7-7의 상위 5단계 호가에 이 조회를 쓴다.
3. **매칭 규칙** (`MatchingEngine`)
   - 들어온 주문(aggressor)은 반대편 최우선 레벨부터 체결한다. 레벨 안에서는 먼저 도착한 주문부터.
   - 지정가 매수는 매도호가 ≤ 지정가인 레벨까지, 지정가 매도는 매수호가 ≥ 지정가인 레벨까지 체결한다. 남은 수량은 자기 가격 레벨의 맨 뒤에 쌓인다.
   - 시장가는 가격 제한 없이 반대편을 소진한다. 남은 수량은 호가창에 쌓지 않고 즉시 취소한다 (이 미션의 규칙, README 2절). 반대편이 비어 있으면 전량 취소한다.
   - 체결가격은 호가창에 있던 주문(resting order)의 가격이다.
   - 체결 1건 = 들어온 주문 1개와 호가창 주문 1개의 짝. 한 주문이 레벨 3개에 걸쳐 체결되면 체결 사건 3건 이상이 생긴다.
4. **자기매매 방지** (이 미션의 규칙, 실제 KRX 제도와 같다고 가정하지 않는다): 체결하려는 상대 주문의 계좌 ID가 들어온 주문의 계좌 ID와 같으면, 그 시점에 들어온 주문의 남은 수량 전부를 취소하고 매칭을 멈춘다. 이미 만들어진 체결은 유지한다. 호가창에 있던 같은 계좌 주문은 그대로 둔다.
5. **엔진 출력 사건** (명령 1개마다 아래 순서로 목록을 돌려준다)
   - `Execution`: 체결 ID(엔진 인스턴스마다 1부터 1씩 증가), 매수 주문 ID, 매도 주문 ID, 매수·매도 계좌 ID, 가격, 수량, aggressor 방향.
   - `OrderRested`: 주문 ID, 가격, 호가창에 쌓인 수량.
   - `OrderCancelled`: 주문 ID, 취소 수량, 사유(`MARKET_REMAINDER`, `SELF_TRADE_PREVENTED`). M7-5에서 `USER_REQUEST`를 추가한다.
   - 순서: 체결 사건들(체결 순서대로) → 마지막에 `OrderRested` 또는 `OrderCancelled` 0~1개. 전량 체결되면 마지막 사건이 없다.
6. **불변식** (모든 명령 처리 직후 성립)
   - (I1) 두 방향 모두 비어 있지 않으면 최우선 매수호가 < 최우선 매도호가
   - (I2) 빈 레벨이 없고, 각 레벨의 잔량 합계 = 그 레벨 주문들의 남은 수량 합
   - (I3) 주문마다 체결 수량 합 + 취소 수량 + 호가창 잔량 = 주문 수량
   - (I4) 지정가 aggressor의 체결가격은 매수면 지정가 이하, 매도면 지정가 이상

## 직접 작성할 테스트 시나리오
아래 참조 시나리오 12개는 **그대로** 테스트로 옮긴다. 이와 별도로 **직접 만든 시나리오 8개 이상**을 `docs/test-scenarios/M7-3.md`에 같은 형식으로 쓰고 리뷰를 받는다.

표기: `B1 매수 10,000×5 (A)` = 주문 ID B1, 계좌 A, 지정가 10,000원, 5주. `MKT` = 시장가. 체결은 `가격×수량 B?↔S?`. B1, S1은 표기용 이름이고 테스트에서는 서로 다른 `long` 주문 ID를 붙인다. 계좌 A~D도 서로 다른 계좌 ID다. 각 시나리오는 새 엔진에서 시작하고 "준비" 주문을 위에서 아래 순서로 넣은 뒤 "실행" 주문을 넣는다. 체결 ID는 1부터 센다. 호가창 표기 `10,000[S2:3]`은 10,000원 레벨에 S2가 3주 남아 있다는 뜻이고, 레벨 안은 왼쪽이 먼저 도착한 주문이다.

| # | 확인하는 규칙 | 준비 | 실행 | 기대 체결 | 실행 후 호가창 / 마지막 사건 |
|---|---|---|---|---|---|
| R1 | 교차하지 않으면 쌓임 | S1 매도 10,010×5 (B) | B1 매수 10,000×5 (A) | 없음 | 매수 10,000[B1:5] / 매도 10,010[S1:5]. `OrderRested(B1, 10,000, 5)` |
| R2 | 같은 가격 전량 체결 | S1 매도 10,000×10 (B) | B1 매수 10,000×10 (A) | #1 10,000×10 B1↔S1 | 양쪽 비어 있음. 마지막 사건 없음 |
| R3 | 호가창 주문의 부분 체결 | S1 매도 10,000×10 (B) | B1 매수 10,000×4 (A) | #1 10,000×4 B1↔S1 | 매도 10,000[S1:6]. 마지막 사건 없음 |
| R4 | 가격 우선 | S1 매도 10,100×5 (B), S2 매도 10,000×5 (C) | B1 매수 10,100×7 (A) | #1 10,000×5 B1↔S2, #2 10,100×2 B1↔S1 | 매도 10,100[S1:3]. 마지막 사건 없음 |
| R5 | 시간 우선 (같은 가격) | S1 매도 10,000×5 (B), S2 매도 10,000×5 (C) | B1 매수 10,000×7 (A) | #1 10,000×5 B1↔S1, #2 10,000×2 B1↔S2 | 매도 10,000[S2:3] |
| R6 | 체결가격 = 호가창 주문 가격 | B1 매수 10,050×10 (A) | S1 매도 9,990×4 (B) | #1 10,050×4 B1↔S1 | 매수 10,050[B1:6] |
| R7 | 지정가 잔량은 자기 가격에 쌓임 | S1 매도 10,000×3 (B) | B1 매수 10,010×10 (A) | #1 10,000×3 B1↔S1 | 매수 10,010[B1:7], 매도 비어 있음. `OrderRested(B1, 10,010, 7)` |
| R8 | 시장가 매수가 여러 레벨 소진, 잔량 취소 | S1 매도 10,000×3 (B), S2 매도 10,010×4 (C), S3 매도 10,050×2 (D) | B1 매수 MKT×12 (A) | #1 10,000×3 B1↔S1, #2 10,010×4 B1↔S2, #3 10,050×2 B1↔S3 | 양쪽 비어 있음. `OrderCancelled(B1, 3, MARKET_REMAINDER)` |
| R9 | 반대편이 빈 시장가 | 없음 | S1 매도 MKT×5 (B) | 없음 | 양쪽 비어 있음. `OrderCancelled(S1, 5, MARKET_REMAINDER)` |
| R10 | 시장가 매도: 높은 가격부터, 같은 가격은 FIFO | B1 매수 9,990×5 (A), B2 매수 10,000×5 (C), B3 매수 10,000×5 (D) | S1 매도 MKT×12 (B) | #1 10,000×5 B2↔S1, #2 10,000×5 B3↔S1, #3 9,990×2 B1↔S1 | 매수 9,990[B1:3]. 마지막 사건 없음 |
| R11 | 자기매매 방지: 첫 상대가 같은 계좌 | S1 매도 10,000×5 (A), S2 매도 10,010×5 (B) | B1 매수 10,010×8 (A) | 없음 | 매도 10,000[S1:5], 10,010[S2:5] 그대로, 매수 비어 있음. `OrderCancelled(B1, 8, SELF_TRADE_PREVENTED)` |
| R12 | 자기매매 방지: 체결 도중 같은 계좌 | S1 매도 10,000×3 (B), S2 매도 10,000×5 (A) | B1 매수 10,000×6 (A) | #1 10,000×3 B1↔S1 | 매도 10,000[S2:5], 매수 비어 있음. `OrderCancelled(B1, 3, SELF_TRADE_PREVENTED)` |

R11에서 S2(계좌 B, 10,010원)는 B1과 체결할 수 있는 가격이지만 4번 규칙상 매칭을 멈추므로 체결되지 않는다.

직접 작성할 8개 이상에 반드시 포함할 경우:
1. 들어온 주문 수량이 한 레벨의 잔량 합과 정확히 같아 그 레벨이 맵에서 사라지는 경우 (I2 확인)
2. 지정가 매수 가격이 최우선 매도호가와 정확히 같은 경우와 1틱 낮은 경우
3. 시장가 주문 수량이 반대편 전체 잔량보다 큰 경우와 정확히 같은 경우
4. 같은 계좌가 매수 레벨 2개에 주문을 가진 상태에서 다른 계좌의 시장가 매도가 두 주문을 모두 체결하는 경우 (자기매매 방지 대상이 아님)
5. 이미 있는 주문 ID로 다시 넣는 경우 → `IllegalArgumentException`, 호가창 변화 없음
6. 매수·매도 양쪽에 각 3개 레벨이 있는 상태에서 레벨 목록 조회 결과(가격 순서, 잔량 합계, 주문 수)
7. 무작위 시험: 시드 42로 만든 명령 10,000건(매수·매도 반반, 지정가 90%·시장가 10%, 가격 9,900~10,100 중 10원 단위, 수량 1~100, 계좌 1~20)을 넣으며 매 명령 뒤 I1~I4 검사
8. 7번을 같은 시드로 두 번 실행하면 체결 사건 목록이 완전히 같은 경우

## 제약
- `OrderBook`, `MatchingEngine`은 스레드 안전하게 만들지 않는다(`synchronized`, `Concurrent*` 금지) — M7-4에서 전용 스레드 1개만 접근한다.
- 엔진 안에서 `System.currentTimeMillis()`, `LocalDateTime.now()`, `Random` 금지 — M7-8 재생 결정성이 깨진다.
- 가격 레벨 탐색을 리스트 전체 정렬로 하지 않는다 — 명령마다 O(레벨 수 × log)가 된다. 정렬된 맵을 쓴다.
- 주문 ID → 주문 찾기용 보조 맵을 써도 된다. 이 맵의 순회 순서로 매칭 순서를 정하지 않는다.
