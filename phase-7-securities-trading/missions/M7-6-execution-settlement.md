# M7-6 체결 반영, 평균단가, 수수료, 세금, T+2 결제

> 가이드 수준: L3, 예상 시간: 7~8h, 선행: M7-2, M7-5

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 체결 1건을 매수, 매도 두 계좌의 예수금, 결제 예정 내역, 보유수량, 평균단가, 실현손익에 한 트랜잭션으로 반영하고, 같은 체결이 두 번 와도 한 번만 반영된다는 것을 테스트로 보여준다
- 3영업일 동안의 매수, 매도 시나리오에서 날짜별 예수금, D+2 예수금, 주문가능금액, 출금가능금액을 손 계산 값과 원 단위까지 일치시킨다
- 영업일 달력으로 결제일을 계산해 월요일 → 수요일, 금요일 → 다음 주 화요일, 휴장일 포함 구간을 테스트로 보여준다

## 배경
체결은 됐는데 계좌에 반영되지 않거나 두 번 반영되면, 고객은 산 주식이 없거나 돈이 두 번 빠진 화면을 본다. 매도 세금을 0.20%로 한 번에 곱하느냐 세목별로 나눠 끝수를 버리느냐만으로도 1원 차이가 나고, 체결 100,000건에서 1원씩 어긋나면 대사(M6-6)에서 최대 100,000원 불일치로 잡힌다.
결제일을 틀리면 출금 가능 금액이 틀려 결제 전 대금이 출금되고, 증권사가 그 돈을 메워야 한다.
M7-4, M7-5에서 사건 소비자가 주문 상태와 홀드만 바꿨다. 이 미션은 같은 소비자에서 실제 돈과 주식을 움직이고, M7-2에서 남겨 둔 "D+2 예수금 = 예수금" 가정을 결제 예정 내역으로 바꾼다.

## 요구사항
개념은 [README](../README.md) 1절, 6절을 먼저 읽는다. 세율 출처는 `fintech-domain-facts` §2(2026년 기준, 확인일 2026-11-10)다.

1. **체결 반영** (`ExecutionHandler`, M7-4 사건 소비자에서 호출)
   - 체결 1건 = DB 트랜잭션 1개: 체결 행 저장 + 매수 계좌 반영 + 매도 계좌 반영 + 두 주문의 체결수량 갱신.
   - 멱등: 체결 행에 `(종목코드, 체결 ID)` 유니크 제약을 두고, 이미 있으면 아무것도 바꾸지 않고 끝낸다. M7-8 재생에서 같은 체결이 다시 오기 때문이다.
   - 두 계좌 행을 잠글 때는 계좌 ID 오름차순으로 잠근다: 종목별 소비자 여러 개가 같은 계좌들을 반대 순서로 잠그면 데드락이 난다(M2-3, M5-9).
2. **금액 규칙**
   - 체결금액 = 체결가 × 체결수량.
   - 수수료 = 체결금액 × 0.015%, 원 미만 절사, 매수, 매도 각각, 체결 1건마다 (이 미션의 규칙, M7-2 `FeePolicy`).
   - 매도 세금: KOSPI는 증권거래세 = 체결금액 × 0.05% 원 미만 절사, 농어촌특별세 = 체결금액 × 0.15% 원 미만 절사, 두 값을 따로 저장한다. KOSDAQ은 증권거래세 = 체결금액 × 0.20% 원 미만 절사. 매수에는 세금이 없다. 세목별 절사는 이 미션의 규칙이다.
3. **매수 쪽 반영**
   - M7-4의 홀드 해제(홀드기준가로 계산한 `홀드(r) − 홀드(r')`)는 그대로 두고, 결제 예정 내역 `−(체결금액 + 수수료)`, 결제일 T+2를 추가한다.
   - 보유수량 += 체결수량. 평균단가 = (기존 수량 × 기존 평균단가 + 체결금액) ÷ (기존 수량 + 체결수량), `BigDecimal` 소수 둘째 자리 `HALF_UP` (수수료 미포함, 이 미션의 규칙).
4. **매도 쪽 반영**
   - 홀드수량 −= 체결수량, 보유수량 −= 체결수량. 결제 예정 내역 `+(체결금액 − 수수료 − 세금 합)`, 결제일 T+2.
   - 평균단가는 바뀌지 않는다. 보유수량이 0이 되면 평균단가를 0.00으로 둔다.
   - 실현손익(원) = (체결금액 − 수수료 − 세금 합) − 평균단가 × 체결수량, 결과를 원 단위 `HALF_UP` (이 미션의 규칙). 체결 행과 보유 행의 누적 실현손익에 기록한다.
5. **영업일과 결제일** (`BusinessCalendar`)
   - 영업일 = 월~금 중 `market_holiday` 테이블에 없는 날. 휴장일 데이터는 Flyway로 넣는 테스트 데이터이며, 이 미션은 실제 KRX 휴장일 목록 전체를 넣지 않는다.
   - 매매일 = 체결 사건의 접수 시각(epoch 밀리초)을 Asia/Seoul로 바꾼 날짜. 결제일 = 매매일 다음부터 센 두 번째 영업일 (T+2, 체결일 포함 3영업일째).
6. **결제 처리** (`SettlementService`): 날짜를 받아 결제일이 그 날짜 이하이고 아직 결제되지 않은 내역을 예수금에 더하고 결제 완료로 표시한다. 같은 날짜로 두 번 실행해도 두 번째는 아무것도 바꾸지 않는다. 운영 실행은 `@Scheduled(cron = "0 0 7 * * MON-FRI", zone = "Asia/Seoul")` (이 미션의 규칙), 테스트는 메서드를 직접 부른다.
7. **잔고 계산** (README 1절 표와 같다)
   - D+2 예수금 = 예수금 + 미결제 내역 합(부호 포함)
   - 주문가능금액 = D+2 예수금 − 홀드금액. M7-2의 주문 접수 검사를 이 식으로 바꾼다.
   - 출금가능금액 = max(0, 예수금 − 미결제 매수 내역 금액 합(양수로) − 홀드금액) (이 미션의 규칙)
8. **API**
   - `GET /api/accounts/{id}/balance` → `cash`, `d2Cash`, `holdAmount`, `orderableCash`, `withdrawableCash` (금액은 Phase 4 M4-6 규칙대로 문자열).
   - `GET /api/accounts/{id}/positions` → 종목별 `quantity`, `holdQuantity`, `sellableQuantity`, `averagePrice`(문자열, 예: `"70266.67"`), `realizedPnl`.
   - `POST /api/accounts/{id}/withdrawals` (본문 `amount`) → 출금가능금액 이하면 예수금에서 빼고 `200`, 넘으면 `422`(`code=INSUFFICIENT_WITHDRAWABLE`), 0 이하면 `400`.
9. **불변식** (통합 테스트 종료 시 검사)
   - (S1) Σ 모든 계좌 D+2 예수금 + Σ 수수료 + Σ 세금 + Σ 출금액 = Σ 초기 입금액
   - (S2) 종목마다 Σ 모든 계좌 보유수량 = 초기 보유수량 합
   - (S3) 체결 행 수 = 엔진이 낸 `Execution` 사건 수 (재전송 포함 여부와 무관)
   - (S4) M7-5의 홀드 불변식

## 제약
- 금액 계산에 `double` 금지. 평균단가만 `BigDecimal`, 나머지 금액은 `long`.
- 세금을 0.20% 한 번에 곱해 나누지 않는다(KOSPI): 세목별 신고 금액과 맞지 않는다.
- 결제일 계산에 `plusDays(2)` 금지: 주말, 휴장일에서 틀린다.
- 체결 반영을 엔진 스레드에서 하지 않는다: M7-4 제약. 반영은 사건 소비자 스레드에서 한다.
