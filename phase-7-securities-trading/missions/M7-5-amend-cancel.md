# M7-5 정정·취소

> 가이드 수준: L3 · 예상 시간: 5~6h · 선행: M7-4

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 취소·정정 명령이 주문 명령과 같은 종목 큐를 거치게 만들고, "체결 후 도착한 취소는 남은 수량만 취소한다"를 큐 순서를 고정한 테스트로 보여준다
- 정정 시 시간 우선순위를 유지하는 경우(같은 가격, 수량 감소)와 잃는 경우(가격 변경, 수량 증가)를 체결 순서로 구분해 보여준다
- 매수 정정에서 홀드 증가분은 엔진 제출 전에, 감소분은 엔진 결과 후에 반영해 주문가능금액이 음수가 되지 않는다는 것을 테스트로 보여준다

## 배경
고객이 취소 버튼을 누르는 순간 그 주문이 체결되고 있을 수 있다. 취소를 엔진 밖에서 DB만 보고 처리하면, 이미 체결된 수량까지 취소된 것으로 기록되어 체결은 됐는데 주식도 돈도 맞지 않는 계좌가 생긴다.
정정도 같다. 가격을 바꾼 주문이 원래 순서를 유지하면, 늦게 낸 사람이 앞줄을 차지하는 불공정이 생긴다.
M7-4에서 모든 주문이 종목별 큐 하나를 거치게 만들었다. 같은 큐로 취소·정정을 보내면 "체결과 취소 중 무엇이 먼저인가"는 큐 순서 하나로 정해진다.

## 요구사항
1. **명령 추가**: `CancelOrder`(주문 ID, 계좌 ID), `AmendOrder`(주문 ID, 계좌 ID, 새 가격, 새 총 주문수량). 정정 요청은 가격과 총 주문수량을 둘 다 보낸다. 바꾸지 않는 값은 현재 값을 그대로 보낸다 (이 미션의 규칙).
2. **취소 규칙** (엔진에서 판정)
   - 호가창에 있는 주문: 남은 수량 전부를 빼고 `OrderCancelled(주문 ID, 남은 수량, USER_REQUEST)`를 낸다. 일부 취소(수량 지정 취소)는 지원하지 않는다. 수량을 줄이려면 정정을 쓴다.
   - 호가창에 없는 주문(전량 체결, 이미 취소, 시장가): `CancelRejected(주문 ID, ORDER_NOT_OPEN)`을 내고 상태를 바꾸지 않는다.
3. **정정 규칙** (이 미션의 규칙. KRX 정정 제도와 같다고 가정하지 않는다)
   - 정정 가능한 주문은 호가창에 있는 지정가 주문뿐이다. 그 외는 `AmendRejected(ORDER_NOT_OPEN)`.
   - 새 미체결수량 = 새 총 주문수량 − 엔진이 처리 시점에 아는 체결수량. 이 값이 0 이하면 `AmendRejected(AMEND_QTY_NOT_ABOVE_FILLED)`.
   - 새 가격·새 총 주문수량이 현재와 모두 같으면 `AmendRejected(AMEND_NO_CHANGE)`.
   - 가격이 같고 총 주문수량이 줄면: 호가창의 자리를 유지한 채 남은 수량만 줄인다.
   - 가격이 바뀌거나 총 주문수량이 늘면: 호가창에서 뺀 뒤 새 가격·새 미체결수량의 지정가 주문으로 다시 들어온 것처럼 M7-3 매칭 규칙(체결가격, 자기매매 방지 포함)을 적용하고, 남은 수량은 새 가격 레벨의 맨 뒤에 쌓는다. 주문 ID는 바뀌지 않는다.
   - 사건: `OrderAmended(주문 ID, 이전 가격, 새 가격, 이전 미체결수량, 새 미체결수량, 우선순위 유지 여부)` → (체결 사건들) → (`OrderRested` 또는 `OrderCancelled`). 거부 시 `AmendRejected(주문 ID, 사유)`만 낸다.
4. **API**
   - `DELETE /api/orders/{orderId}?accountId={id}` → 취소, `PATCH /api/orders/{orderId}` (본문: `accountId`, `price`, `quantity`) → 정정.
   - 큐에 넣기 전 DB로 확인: 주문이 없거나 계좌가 다르면 `404`, DB 상태가 종료 상태(`FILLED`, `CANCELLED`, `REJECTED`)면 `409`(`code=ORDER_NOT_OPEN`), 정정 가격이 M7-1 검증(호가단위, 가격제한폭)에 실패하면 `422`. DB 기준으로 새 값이 현재와 같으면 `422`(`code=AMEND_NO_CHANGE`).
   - 큐 제출 성공 → `202`. 결과는 사건 소비자가 `orders` 테이블에 반영하고, 클라이언트는 `GET /api/orders/{orderId}`로 확인한다. 제출 실패 → `503`(`ENGINE_BUSY`), 이때 3번의 예약 홀드를 되돌린다.
   - DB 확인을 통과해도 엔진에서 거부될 수 있다(그 사이 체결). 이 경우 주문 상태는 바뀌지 않고, 정정 거부 사유를 주문 이력에 남긴다.
5. **정정과 홀드** (이 미션의 규칙)
   - 매수 정정의 필요 홀드 = M7-2 공식(`새 가격 × 새 미체결수량 + 수수료`). 새 미체결수량은 API 시점의 DB 체결수량으로 계산한다.
   - 필요 홀드가 현재 주문 홀드보다 크면, 차액을 **엔진 제출 전에** 같은 DB 동시성 방식(M7-2)으로 추가 차감한다. 주문가능금액이 모자라면 `422`(`INSUFFICIENT_CASH`)로 거부하고 제출하지 않는다. 매도 정정의 수량 증가도 같은 방식으로 매도가능수량에서 먼저 차감한다(`INSUFFICIENT_QUANTITY`).
   - 엔진이 `OrderAmended`를 내면, 사건 소비자가 그 주문의 홀드를 `새 가격 × (사건의 새 미체결수량) + 수수료`로 다시 계산하고 예약분을 포함해 차이를 정리한다. 줄어드는 홀드는 **이 시점에만** 해제한다.
   - 엔진이 `AmendRejected`를 내거나 제출이 실패하면 예약한 차액을 전부 되돌린다.
   - M7-2 불변식을 이렇게 바꾼다: `계좌 홀드금액 = Σ(미체결 매수 주문 홀드) + Σ(처리 대기 중인 정정 예약 홀드)`.
6. **취소·체결과 홀드**: M7-4에서 만든 사건 소비자의 홀드 해제 처리(`Execution`, `OrderCancelled`)를 사유 `USER_REQUEST`에도 그대로 적용한다. 정정 이후의 체결은 정정된 가격을 홀드기준가로 써서 해제 금액을 계산한다.

## 직접 작성할 테스트 시나리오
`docs/test-scenarios/M7-5.md`에 표를 쓰고 리뷰를 받은 뒤 구현한다. **최소 14개**. 경합 시나리오는 스레드 타이밍에 기대지 말고 명령을 정해진 순서로 엔진에 넣어 재현한다. 반드시 포함할 경우 (`A00002`, 계좌 A·B·C):

1. 부분 체결 후 취소: B1 매수 10,000×10(A, 홀드 100,015) → S1 매도 10,000×4(B) → B1 취소 ⇒ `OrderCancelled(B1, 6, USER_REQUEST)`, B1 `CANCELLED` 체결 4·취소 6, 체결로 해제 40,006, 취소로 해제 60,009, A의 홀드금액 0
2. 전량 체결 후 취소: B1 매수 10,000×10 → S1 매도 10,000×10 → B1 취소 ⇒ `CancelRejected(ORDER_NOT_OPEN)`, B1 `FILLED`, 홀드 변화 없음
3. 취소 후 들어온 반대 주문: B1 매수 10,000×10 → B1 취소 → S1 매도 10,000×10 ⇒ 체결 없음, 매도 10,000[S1:10]
4. 같은 주문 두 번 취소 ⇒ 두 번째는 `CancelRejected(ORDER_NOT_OPEN)`, 홀드 해제는 한 번만
5. 수량 감소는 자리 유지: B1 매수 10,000×10(A), B2 매수 10,000×10(C) → B1 총수량 6으로 정정 → S1 매도 10,000×8(B) ⇒ 매수 10,000[B1:6, B2:10]이 된 뒤 체결 #1 10,000×6 B1↔S1, #2 10,000×2 B2↔S1
6. 수량 증가는 맨 뒤로: B1 매수 10,000×5(A), B2 매수 10,000×5(C) → B1 총수량 8로 정정 → S1 매도 10,000×6(B) ⇒ 매수 10,000[B2:5, B1:8]이 된 뒤 체결 #1 10,000×5 B2↔S1, #2 10,000×1 B1↔S1
7. 가격 정정으로 즉시 체결: B1 매수 9,990×5(A), S1 매도 10,000×3(B) → B1 가격 10,000으로 정정 ⇒ 체결 10,000×3 B1↔S1, 매수 10,000[B1:2]
8. 체결과 정정의 경합: B1 매수 10,000×10 → S1 매도 10,000×7 → B1 총수량 6으로 정정 ⇒ `AmendRejected(AMEND_QTY_NOT_ABOVE_FILLED)`, B1 미체결 3 그대로. 같은 상황에서 총수량 8로 정정 ⇒ 새 미체결 1, 자리 유지
9. 매수 가격 인하 정정의 홀드 해제: B1 매수 10,000×10(홀드 100,015) → 가격 9,990으로 정정 ⇒ 새 홀드 99,914, `OrderAmended` 처리 후 101원 해제, 우선순위 잃음
10. 홀드 부족 정정: 예수금 100,015원, B1 매수 10,000×10(주문가능금액 0) → 가격 10,010으로 정정 요청 ⇒ 필요 홀드 100,115로 차액 100원 부족, `422 INSUFFICIENT_CASH`, 큐 제출 없음
11. 예약 후 엔진 거부: 가격 인상 정정으로 차액을 예약한 뒤, 정정 명령보다 앞서 큐에 들어간 매도가 B1을 전량 체결 ⇒ `AmendRejected(ORDER_NOT_OPEN)`, 예약 차액 전부 반환, 계좌 홀드금액 0
12. 종료 상태 주문 취소 API ⇒ `409 ORDER_NOT_OPEN`, 큐 제출 없음
13. 다른 계좌의 주문 취소 API ⇒ `404`
14. 무작위 경합: 주문 스레드 4개(각 2,000건), 취소 스레드 2개, 정정 스레드 1개를 30초 동안 실행 → 모든 명령 처리 후 주문마다 `체결 + 취소 + 미체결 = 총 주문수량`, `Σ 매수 체결수량 = Σ 매도 체결수량`, 5번의 바뀐 홀드 불변식, M7-3 I1~I4가 성립

계산: 1번 홀드 100,015 = 100,000 + 15. 4주 체결 후 남은 홀드 = 60,000 + 9 = 60,009, 체결 해제 100,015 − 60,009 = 40,006. 9번 새 홀드 = 99,900 + 14(14.985 절사) = 99,914. 10번 필요 홀드 = 100,100 + 15(15.015 절사) = 100,115.

## 제약
- 취소·정정을 DB 상태만 바꿔서 처리하지 않는다 — 엔진 호가창에 주문이 남아 체결될 수 있다.
- 줄어드는 홀드를 엔진 제출 전에 해제하지 않는다 — 엔진이 정정을 거부하면 홀드보다 큰 주문이 호가창에 남는다.
- 경합 테스트에 `Thread.sleep`을 쓰지 않는다. 고정 순서 테스트는 엔진에 직접 명령을 넣고, 무작위 경합 테스트는 끝난 뒤 불변식만 검사한다.

## 생각해볼 질문
1. 수량 증가 정정이 우선순위를 잃지 않는다면, 1주짜리 주문을 미리 내 두고 나중에 1만 주로 늘리는 방식으로 어떤 이득을 얻을 수 있는가?
2. 정정을 "취소 + 새 주문" 두 명령으로 나눠 보내면, 두 명령 사이에 다른 명령이 끼어들 때 어떤 결과가 생기는가? 이 미션처럼 명령 하나로 처리하는 것과 비교한다.
3. Phase 8에서 홀드가 계좌 서비스에, 정정이 주문 서비스에 있으면 "증가분은 먼저 예약, 감소분은 결과 후 해제" 규칙을 서비스 간 메시지 몇 개로 구현해야 하는가? 메시지 하나가 유실되면 어느 쪽 금액이 틀어지는가?
