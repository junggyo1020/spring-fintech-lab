# M7-8 이벤트 소싱 복구

> 가이드 수준: L3 · 예상 시간: 6~7h · 선행: M7-5

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- 엔진이 명령을 처리하기 전에 명령 로그에 추가(append)하고, 재시작 시 로그를 재생해 호가창을 복구한다
- 명령 10만 건을 처리한 원본 엔진, 로그 전체를 재생한 엔진, 스냅샷 + 꼬리 로그로 복구한 엔진의 호가창 해시와 체결 해시가 모두 같다는 것을 테스트로 보여준다
- 마지막 줄이 반쯤 쓰인 로그는 그 줄만 버리고 복구하고, 중간 줄이 깨진 로그는 시작을 거부한다는 것을 테스트로 보여준다
- fsync 방식 2가지의 처리량과 전원 장애 시 잃을 수 있는 범위를 표로 비교한다

## 배경
매칭 엔진의 호가창은 메모리에만 있다. 프로세스가 죽으면 고객이 낸 미체결 주문이 사라지고, DB에는 `RECEIVED`로 남은 주문과 홀드만 남는다. 고객은 돈이 묶였는데 호가창에 주문이 없는 상태가 된다.
DB에 호가창을 매 명령 저장하면 M7-4에서 측정한 처리량이 DB 왕복 시간으로 떨어진다. 그래서 거래소 엔진은 입력 명령을 순서대로 파일에 남기고, 재시작 때 그 순서로 다시 실행해 상태를 만든다.
M7-3에서 엔진 안에 시계·난수를 쓰지 않았고, M7-4에서 처리 순서를 시퀀스 번호 하나로 정했다. 이 미션은 그 두 결정 덕분에 재생이 같은 결과를 낸다는 것을 테스트로 증명한다.

## 요구사항
개념은 [README](../README.md) 8절을 먼저 읽는다. 패키지는 `lab.trading.engine.journal`.

1. **명령 로그** (`CommandJournal`)
   - 종목마다 파일 1개: `data/engine/{종목코드}/commands.log`. 한 줄에 명령 1개(JSON Lines), 줄 끝은 `\n`.
   - 줄 내용: 시퀀스 번호, 명령 종류(`PLACE`, `CANCEL`, `AMEND`), 접수 시각(epoch 밀리초), 명령 필드 전부. 조회 명령(M7-7 (나), 해시 조회)은 기록하지 않는다.
   - 순서: 엔진 스레드가 시퀀스를 붙임 → 로그에 추가 → 엔진 실행 → 사건 출력. 로그 추가가 `IOException`으로 실패하면 그 종목 엔진은 정지 상태가 되고 이후 제출은 모두 `ENGINE_BUSY`로 거부한다. 정지 상태는 재시작으로만 풀린다 (이 미션의 규칙).
2. **fsync 방식** (설정 `trading.journal.fsync`)
   - `EVERY_COMMAND`: 줄을 쓸 때마다 `FileChannel.force(false)`.
   - `OS_BUFFERED`: `force`를 부르지 않는다. 운영체제가 페이지 캐시를 디스크에 쓰는 시점에 맡긴다.
   - 기본값은 `EVERY_COMMAND`. 테스트 속도를 위해 테스트 프로파일만 `OS_BUFFERED`를 쓸 수 있다.
3. **스냅샷** (`SnapshotStore`)
   - N = 10,000 (이 미션의 규칙): 시퀀스가 10,000의 배수인 명령을 처리한 직후 엔진 스레드에서 스냅샷을 쓴다.
   - 내용: 마지막 시퀀스, 다음 체결 ID, 호가창 전체(방향별·가격별·도착 순서별 주문의 주문 ID, 계좌 ID, 방향, 가격, 주문수량, 체결수량, 남은 수량).
   - 쓰기: 임시 파일에 다 쓴 뒤 `Files.move(..., ATOMIC_MOVE)`로 `snapshot-{시퀀스 12자리 0채움}.json`으로 바꾼다. 반쯤 쓰인 스냅샷 파일이 정식 이름으로 보이는 일이 없게 하기 위해서다. 최신 2개만 남기고 오래된 것은 지운다.
4. **복구** (`EngineRecovery`, `SymbolEngine` 시작 전에 실행)
   - 정식 이름의 스냅샷 중 시퀀스가 가장 큰 것을 읽는다. 읽기에 실패하면 그다음 스냅샷, 모두 실패하면 빈 호가창에서 시작한다.
   - 로그에서 스냅샷 시퀀스보다 큰 줄을 순서대로 재생한다. 시퀀스가 1씩 이어지지 않으면 `CorruptedJournalException`(빠진 시퀀스 번호 포함)으로 시작을 거부한다.
   - 마지막 줄이 `\n`으로 끝나지 않거나 JSON으로 읽히지 않으면 그 줄을 파일에서 잘라내고(truncate) 경고 로그를 남긴 뒤 계속한다. 마지막이 아닌 줄이 읽히지 않으면 `CorruptedJournalException`(줄 번호 포함)으로 시작을 거부한다.
   - 복구가 끝난 뒤 새 명령의 시퀀스는 로그의 마지막 시퀀스 + 1부터 이어진다.
5. **재생 사건의 처리**: 재생으로 나온 사건도 M7-4 사건 출력 큐로 보낸다. 장애 직전에 로그에는 남았지만 계좌에 반영되지 않은 사건이 있을 수 있기 때문이다.
   - 사건마다 (시퀀스, 명령 안에서의 순번)을 붙인다. 사건 소비자는 종목별로 마지막으로 반영한 (시퀀스, 순번)을 `engine_offset` 테이블에 저장하고, 그 사건의 반영과 같은 트랜잭션에서 갱신한다. 저장된 값 이하인 사건은 건너뛴다.
   - M7-6의 체결 유니크 제약은 그대로 둔다. `OrderCancelled`, `OrderAmended`처럼 유니크 키가 없는 사건의 중복 반영(홀드 이중 해제)을 `engine_offset`이 막는다.
6. **상태 해시**: 아래 형식의 문자열을 UTF-8로 바꿔 SHA-256을 구하고 16진수 소문자로 표현한다. 줄 구분은 `\n`.
   - 호가창 해시: `LAST_SEQ|{n}`, `NEXT_EXEC_ID|{n}`, 이어서 매수 레벨을 최우선부터 레벨 안 도착 순서로 `B|{가격}|{주문 ID}|{계좌 ID}|{남은 수량}`, 매도도 같은 방식으로 `A|...`.
   - 체결 해시: 체결 ID 순서로 `E|{체결 ID}|{매수 주문 ID}|{매도 주문 ID}|{가격}|{수량}`.
   - 해시 조회 API `GET /api/engine/{종목코드}/state-hash`는 조회 명령을 큐에 넣어 엔진 스레드에서 계산한다.
7. **명령 생성기** (테스트 지원 코드): 시드 7로 명령 100,000건을 만든다. 구성: `PLACE` 85%(M7-3 무작위 시험과 같은 분포), `CANCEL` 10%(이미 만든 주문 ID 중 무작위), `AMEND` 5%(이미 만든 주문 ID 중 무작위, 가격 9,900~10,100 중 10원 단위, 총 수량 1~100). 거부되는 취소·정정이 섞여도 된다 — 거부도 결정적이어야 한다.

## 직접 작성할 테스트 시나리오
`docs/test-scenarios-M7-8.md`에 표를 쓰고 리뷰를 받은 뒤 구현한다. **최소 10개**. 반드시 포함할 경우:

1. 결정성: 생성기 명령 100,000건을 엔진 A(로그 기록)로 처리 → 로그만으로 엔진 B 복구(스냅샷 삭제) → 시퀀스 100,000 스냅샷(`snapshot-000000100000.json`, 100,000번째 명령 직후에 생긴다)을 지운 뒤 시퀀스 90,000 스냅샷 + 꼬리 10,000건으로 엔진 C 복구. A·B·C의 호가창 해시가 같고, A와 B의 체결 해시가 같으며, C가 재생한 체결 목록은 A의 체결 중 시퀀스 90,000 초과분과 같다
2. 같은 명령 목록을 서로 다른 날짜에 실행한 두 엔진(테스트에서 `Clock`만 다르게 주입)의 해시가 같다 — 엔진이 시계를 읽지 않는다는 증거. 접수 시각은 명령에 담긴 값을 쓴다
3. 마지막 줄 절반 손상: 로그 끝에 `\n` 없는 JSON 조각을 덧붙임 → 복구 성공, 파일에서 그 조각이 잘려 나감, 다음 명령 시퀀스 = 마지막 정상 시퀀스 + 1
4. 중간 줄 손상 (스냅샷을 모두 지운 상태): 50,000번째 줄을 `{"seq":` 로 바꿈 → `CorruptedJournalException`, 메시지에 줄 번호 50000
5. 시퀀스 빠짐 (스냅샷을 모두 지운 상태): 40,000번째 줄 삭제 → `CorruptedJournalException`, 메시지에 시퀀스 40000
6. 최신 스냅샷 파일 손상(내용 일부 삭제) → 그 이전 스냅샷 + 더 긴 꼬리로 복구, 해시는 1번과 같다
7. 스냅샷 쓰는 도중 실패 재현(임시 파일만 남기고 이동 전 중단) → 정식 이름 스냅샷 목록에 나타나지 않는다
8. 재생 사건 중복 반영 방지: 계좌 반영까지 끝난 상태에서 엔진만 재시작해 재생 → 예수금·홀드·보유수량·체결 행 수가 재시작 전과 같다
9. 반영 누락 복구: 사건 소비자를 멈춘 채 명령 100건을 처리하고 프로세스를 종료 → 재시작 후 재생 사건으로 100건 분량이 모두 반영되고 M7-6 S1~S4가 성립
10. 실제 강제 종료: 애플리케이션을 띄우고 주문 5,000건을 보낸 뒤 `state-hash`를 기록 → `kill -9 <pid>` → 재시작 후 `state-hash`가 같다 (수동 실행 절차와 결과를 `docs/recovery-report.md`에 기록)

## 제약
- 호가창 상태 자체를 DB에 매 명령 저장하지 않는다 — 이 미션은 명령 로그가 원본이다.
- 로그 파일을 덮어쓰거나 중간을 고치지 않는다. 허용되는 변경은 끝에 추가하기와 4번의 손상된 마지막 줄 잘라내기뿐이다.
- 재생 중에 `Clock`, `Random`, `UUID.randomUUID()`를 엔진에서 호출하지 않는다.
- 복구 테스트에서 엔진 객체를 재사용하지 않는다. 매번 새 인스턴스를 만든다.
