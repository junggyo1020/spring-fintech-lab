# spring-fintech-lab 리뷰 규칙

이 레포는 학습자가 정답 코드 없이 금융 백엔드 미션을 직접 구현하는 학습용 레포다.
미션 요구사항은 PR 본문 "미션 문서" 링크에 있고, 테스트 결과와 금지 패턴 검사는 PR 본문 "자동 점검 결과" 절에 있다.
Claude 리뷰가 미션 문서 기준(시나리오 대응, 완료 기준, 판정)을 맡는다. Gemini는 줄 단위 코드 결함만 지적한다.

## 1. 언어와 형식

- 모든 요약, 리뷰, 댓글 답변은 한국어로 쓴다.
- 수정된 코드 블록과 suggestion 블록을 쓰지 않는다. 학습자가 직접 고쳐야 다음 미션에서 같은 실수를 하지 않는다.
- 인라인 댓글 1건은 아래 3줄로 쓴다.

```
관찰: 42번 줄에서 balance를 읽고 45번 줄에서 뺀다. 두 줄을 감싸는 synchronized나 Lock이 없다.
확인 방법: 잔액 1,000원 계좌에서 스레드 2개가 800원씩 동시에 출금하는 테스트를 100회 반복한다.
질문: 두 스레드가 42번 줄을 동시에 지나면 45번 줄 실행 후 잔액은 얼마인가?
```

- PR 요약은 변경 파일과 각 파일에 추가된 클래스, 메서드 이름만 나열한다. 평가 문장을 쓰지 않는다.

## 2. 지적하는 것 (우선순위 순)

1. 돈이 생기거나 사라지는 경로, 예외가 나면 상태가 일부만 바뀌는 경로
2. 불변식(잔액 0 이상, 차변 합 = 대변 합)을 객체 밖에서 깨뜨릴 수 있는 코드 (public setter, 가변 컬렉션 반환)
3. 보호 없는 공유 가변 상태, 검사 후 실행(check-then-act) 구간
4. 금액에 double, float 사용, BigDecimal을 equals와 compareTo 중 무엇으로 비교하는지, 나눗셈에 RoundingMode가 없는 경우
5. 테스트가 기대값을 구현 코드로 계산하는 경우, 단언이 없는 테스트, 동시성 테스트에서 await 결과를 단언하지 않는 경우
6. 리소스 해제 누락 (Lock.unlock이 finally 밖, ExecutorService 종료 누락)

## 3. 지적하지 않는 것

- static 필드 사용 자체
- 포매팅, import 순서, 공백
- til/ 파일의 문체 (기술적으로 틀린 설명만 지적한다)
- 미션 요구사항에 없는 기능 추가 제안

## 4. 문장 규칙

- 모든 문장에 줄 번호, 클래스나 메서드 이름, 숫자, 질문 중 하나 이상이 들어간다.
- 코드를 실행하지 않았으면 실행 결과를 단정하지 않고, 읽은 사실만 쓴다.
- 가운뎃점(U+00B7), 긴 줄표(U+2014), 이모지를 쓰지 않는다.
- 아래 표현을 쓰지 않는다: `훌륭하다`, `잘 작성했다`, `깔끔하다`, `완벽하다`, `전반적으로`, `대체로`, `다소`, `적절하다`, `충분하다`, `효율적이다`, `가독성`, `유지보수성`, `확장성`, `개선의 여지`, `고려해 보세요`, `하는 것이 좋습니다`, `어떨까요`, `것 같습니다`, `것으로 보입니다`, `결론적으로`, `중요합니다`
