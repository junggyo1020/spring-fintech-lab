# 미션 문서 템플릿

`{}` 부분을 채운다. 섹션 순서와 제목(`##`)은 바꾸지 않는다. `scripts/check_docs.py`가 제목으로 구조를 검사한다.

```markdown
# M{P}-{N} {제목}

> 가이드 수준: L{1|2|3} · 예상 시간: {a}~{b}h · 선행: {M?-?, M?-? 또는 없음}

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- {동사로 끝나는 관찰 가능한 행동. 예: "`SELECT ... FOR UPDATE`가 잡는 락 범위를 `performance_schema.data_locks` 조회 결과로 보여준다"}
- {2~4개}

## 배경
{이 미션이 다루는 문제가 실제 금융 시스템에서 어떤 사고로 이어지는지 3~6문장. 이전 미션과의 연결 한 문장.}

## 요구사항
{번호 목록. 각 항목은 입력·출력·예외가 정해져 있어야 한다. 클래스/메서드/엔드포인트 이름을 코드 서식으로 적는다.}
{L1: 시그니처 전부 제공 / L2: 핵심 인터페이스만 / L3: 기능·불변식만}

## 테스트 시나리오
{L1·L2: 아래 표. 기대값은 전부 구체 값(숫자, 예외 클래스명, HTTP 상태 코드).}

| # | 준비(Given) | 실행(When) | 기대 결과(Then) |
|---|---|---|---|
| 1 | {} | {} | {} |

{L3에서는 이 섹션 제목을 "## 직접 작성할 테스트 시나리오"로 바꾸고, 표 대신 "반드시 포함할 경우" 목록(최소 개수 명시)을 준다.}

## 제약
- {금지 사항과 이유. 예: "`double` 사용 금지 — 2진 부동소수점 오차"}

## 힌트
<details>
<summary>힌트 1: {무엇에 대한 힌트인지}</summary>

{정답 코드가 아니라 사용할 API 이름, 확인할 문서 위치, 생각할 질문}
</details>

## 완료 기준
- [ ] {명령어 또는 관찰 가능한 결과. 예: "`./gradlew test`에서 이 미션의 테스트 14개가 통과한다"}
- [ ] {측정표·문서가 있으면 파일 경로와 필수 열을 명시}

## 생각해볼 질문
1. {TIL에 답할 질문. "왜"와 "다른 선택지와 비교"를 묻는다}
```

## 섹션별 작성 기준

| 섹션 | 기준 |
|---|---|
| 목표 | "이해한다", "익힌다", "안다"를 쓰지 않는다. 다른 사람이 보고 확인할 수 있는 행동으로 쓴다 |
| 요구사항 | 경계값(0, 음수, null, 최대값, 같은 계좌 이체)의 동작을 모두 정한다. 정하지 않으면 학습자마다 다른 테스트가 나온다 |
| 테스트 시나리오 | 기대값은 구현 코드가 아니라 손 계산 또는 스크립트로 구한다. 계산 과정이 3단계 이상이면 표 아래에 계산식을 적는다 |
| 힌트 | 정답 코드를 쓰지 않는다. API 이름, Javadoc/공식 문서 섹션 이름, 확인용 질문까지만 쓴다 |
| 완료 기준 | 체크박스마다 "무엇을 실행하면 무엇이 보이는가"가 있어야 한다 |
| 생각해볼 질문 | 2~4개. 다음 Phase로 이어지는 질문을 1개 포함한다 |

## 성능 측정이 있는 미션

측정 규칙을 미션 안에 적는다: 워밍업 3회 실행 후 5회 측정, 중앙값 기록, JDK 버전·CPU 코어 수·OS를 표 위에 적는다.
측정표의 열 이름을 미리 정해준다.
