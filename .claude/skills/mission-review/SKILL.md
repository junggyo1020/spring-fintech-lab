# 미션 코드 리뷰

목표는 학습자가 **다음 미션을 혼자 풀 수 있게** 만드는 것이다. 정답 코드를 주면 이번 미션은 통과해도 다음 미션의 같은 지점에서 다시 막힌다.
그래서 지적 1건은 "어디서(`파일:줄`), 무엇을 관찰했고, 학습자가 어떻게 직접 확인할 수 있으며, 무엇을 스스로 답해야 하는가"로 구성한다.

문장은 [references/writing-rules.md](references/writing-rules.md)를 따른다. 보고서를 올리기 전에 `scripts/check_text.py`로 검사할 수 있으면 검사하고 위반을 0건으로 만든다.

## 1. 입력 모으기

| 입력 | 위치 | 쓰는 곳 |
|---|---|---|
| 미션 문서 | PR 본문 "미션 문서" 링크, 또는 `phase-*/missions/M{P}-{N}-*.md` | 요구사항, 제약, 테스트 시나리오, 완료 기준 |
| 커리큘럼 맵 | `docs/curriculum-map.md` | 다른 미션을 가리킬 때 미션 번호 확인 |
| 변경 코드 | `gh pr diff`, 또는 `git diff origin/main...HEAD` | 지적 대상 |
| PR 본문 자동 점검 | "자동 점검 결과" 절 (테스트, 시나리오 대응, 커밋 순서, 금지 패턴) | 실행 결과로 인용 |
| CI 결과 | `gh pr checks` | 판정 |
| 이전 리뷰 | `gh pr view --comments`에서 이 스킬 형식의 보고서 | 재리뷰 대조표, 힌트 단계 |
| 리뷰 반영 기록 | PR 본문 "리뷰 반영 기록" 표 | 재리뷰 대조표 |

로컬 세션에서는 해당 workspace에서 `./gradlew test`를 실행해 통과, 실패 개수를 기록한다. 동시성 미션은 `--rerun-tasks`로 3회 실행해 결과가 같은지 본다. GitHub Actions 안에서는 직접 실행하지 않고 PR 본문과 CI 결과를 인용한다.

## 2. 지적 등급

| 등급 | 해당하는 경우 (하나라도 해당하면 그 등급) |
|---|---|
| 필수 | 미션 완료 기준 미충족 / 돈이 생기거나 사라지는 경로 / 예외 발생 시 상태가 일부만 바뀜 / 불변식(잔액 0 이상, 차변 합 = 대변 합 등)을 객체 밖에서 깨뜨릴 수 있음 / 보호 없는 공유 가변 상태 / 금액에 `double`, `float` 사용 / 테스트가 기대값을 구현 코드로 계산하거나 단언이 없음 / 미션 제약 위반 |
| 권장 | 미션 시나리오 외 경계값(0, 정확히 잔액, 잔액+1, 자정) 테스트 누락 / 계층 의존 방향(도메인이 Spring, DB를 참조) / 예외 계층과 메시지 / 이름 / 중복 코드 |
| 질문 | 코드만으로 의도를 알 수 없어 학습자의 설명이 필요한 부분 |

`static` 필드 사용 자체, 포매팅, import 순서는 지적하지 않는다.
권장은 위험이 큰 순서로 최대 5건만 적는다. 학습자가 한 번에 처리할 수 있는 양을 넘기면 필수 지적이 묻힌다. 같은 이유로 필수도 아래 규칙으로 줄인다.

1. 원인이 같은 지적은 1건으로 묶는다. 예: "생성자가 잔액을 받는다"와 "`open` 팩터리가 없다"는 둘 다 "계좌 생성 경로가 요구사항 5와 다르다" 1건이다. 관찰에 줄 번호를 모두 적는다.
2. 완료 기준 표에서 이미 미충족으로 보인 항목(시나리오 누락 번호, 커밋 순서)은 필수 지적으로 다시 쓰지 않는다. 코드 위치를 짚어야 하는 경우만 지적으로 쓴다.
3. 요구사항의 클래스나 시나리오가 절반 넘게 없으면 "제출 범위가 요구사항의 절반 미만" 1건으로 쓰고, 나머지 필수는 정합성, 불변식, 동시성, 금액 타입에 해당하는 것만 적는다.

## 3. 지적 1건의 형식

아래 예시는 2회차에도 미해결이라 힌트 2단계(4절)가 적용된 지적이다. 1회차 지적에는 "참고" 줄이 없다.

```markdown
**[필수 1] `Account.java:42` 잔액 검사와 차감 사이에 잠금이 없다 (2회차 미해결)**
- 관찰: 42번 줄에서 `balance`를 읽고 45번 줄에서 뺀다. 두 줄을 감싸는 `synchronized`나 `Lock`이 없다.
- 확인 방법: 잔액 1,000원 계좌에서 스레드 2개가 800원씩 동시에 출금하는 테스트를 100회 반복한다.
- 질문: 두 스레드가 42번 줄을 동시에 지나면 45번 줄 실행 후 잔액은 얼마인가?
- 참고: Phase 2 README 3절
```

| 항목 | 규칙 |
|---|---|
| 제목 | `[등급 번호] 파일:줄 관찰 요약` 한 줄. 번호는 재리뷰 대조에 쓰므로 등급별로 1부터 매긴다 |
| 관찰 | 코드에서 읽은 사실만. 줄 번호와 식별자를 넣는다 |
| 확인 방법 | 학습자가 직접 실행할 테스트 조건이나 명령. 정답 코드는 넣지 않는다 |
| 질문 | 1개. 답하면 문제의 원인을 학습자가 설명하게 되는 질문 |
| 참고 | 힌트 단계(4절)가 2 이상일 때만. 확인한 README 절 번호, 미션 번호, 공식 문서 절 이름 |

GitHub에서는 같은 내용을 해당 줄 인라인 댓글로도 남긴다. 인라인 댓글에는 제목 줄 없이 관찰, 확인 방법, 질문만 쓴다.

## 4. 힌트 단계

같은 지적(같은 파일의 같은 문제)이 이전 리뷰에 있었는데 해결되지 않았으면 단계를 올린다.

| 단계 | 조건 | 추가로 주는 것 |
|---|---|---|
| 1 | 처음 지적 | 관찰, 확인 방법, 질문 |
| 2 | 2번째 리뷰에서도 미해결 | + README 절 번호 또는 미션 번호 |
| 3 | 3번째 리뷰에서도 미해결, 또는 학습자가 "3번 막혔다"고 말함 | + 써야 할 API, 클래스 이름과 공식 문서 절 이름. 그래도 코드는 쓰지 않는다 |

## 5. 보고서 형식

```markdown
## M{P}-{N} 리뷰 ({n}회차, {YYYY-MM-DD})

**판정: {머지 가능 | 수정 필요}** (필수 {a}건, 미충족 완료 기준 {b}개, CI {통과 | 실패 | 없음})

### 실행 결과
- 테스트: 통과 {x}, 실패 {y}, 건너뜀 {z} (출처: PR 본문 자동 점검 | 로컬 실행 3회)
- 시나리오 대응: {m}개 중 {k}개 있음. 없는 번호: {목록 | 없음}
- 커밋 순서: {첫 [test] 커밋이 첫 구현 커밋보다 먼저 있음 | 먼저 있지 않음 | 해당 없음(M0-1, M0-3, M5-1처럼 직접 실행해 확인하는 미션)}

### 이전 지적 대조 (2회차부터)
| 이전 번호 | 지적 요약 | 상태 | 근거 |
|---|---|---|---|
| 필수 1 | `Account.java:42` 잠금 없음 | 해결 | `Account.java:40` `synchronized` 추가, 반복 테스트 `#18` |

### 완료 기준
| 기준 | 상태 | 근거 |
|---|---|---|

### 필수
(3절 형식)

### 권장
(3절 형식, 최대 5건)

### 질문
(3절 형식에서 확인 방법 생략 가능)

### 유지할 것
- `파일:줄` 지킨 규칙 이름 (예: "`Money.java:12` 문자열 생성자로 `BigDecimal` 생성, M1-1 제약 2"). 최대 2건. 평가 형용사를 쓰지 않는다

### 다음에 읽을 것
- 위 지적과 관련된 README 절 번호 또는 self-check 항목. `docs/curriculum-map.md`에서 확인한 것만

### weakness.md 후보
`{YYYY-MM-DD} | M{P}-{N} | {틀린 내용} | (수정 후 학습자가 작성)`
```

판정 규칙: 필수 0건, 완료 기준 전부 충족, CI 통과(또는 CI가 아직 없는 M0-1~M0-2)일 때만 "머지 가능"이다. 하나라도 아니면 "수정 필요"다.
"weakness.md 후보"는 이전 리뷰와 같은 유형의 필수 지적이 반복됐을 때만 적는다. "올바른 내용" 칸을 비워 두는 이유는 학습자가 고친 뒤 자기 말로 쓰게 하기 위해서다.

## 6. L3 테스트 시나리오 표 리뷰

구현 전 Draft PR로 `docs/test-scenarios/M{P}-{N}.md`만 올라온 경우다.

1. 미션의 "반드시 포함할 경우" 번호마다 대응하는 시나리오 행이 있는지 표로 만든다.
2. 행마다 준비, 실행, 기대 결과 3칸이 숫자로 채워졌는지 본다. "정상 처리된다" 같은 기대 결과는 필수 지적이다.
3. 빠진 경우는 "잔액이 정확히 이체 금액과 같으면 기대 결과는 무엇인가?"처럼 조건을 담은 질문으로 제시한다.

## 7. 힌트 요청이나 질문 이슈에 답할 때

로컬 세션의 "힌트 줘" 요청과 GitHub 질문 이슈(`.github/ISSUE_TEMPLATE/question.yml`)의 `@claude` 댓글에 적용한다.
리뷰 보고서 대신 지적 1건 형식(3절)으로 답한다. 질문 이슈의 "시도한 것", "실제 결과" 칸이 비어 있거나 학습자가 무엇을 시도했는지(명령, 에러 원문)를 아직 말하지 않았으면 그것부터 묻는다.
같은 질문 이슈에서 3번째 답부터는 4절 힌트 3단계(API, 클래스 이름과 공식 문서 절 이름)까지 준다.
