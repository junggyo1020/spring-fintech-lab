# 미션 코드 리뷰

목표는 학습자가 **다음 미션을 혼자 풀 수 있게** 만드는 것이다. 정답 코드를 주면 이번 미션은 통과해도 다음 미션에서 같은 곳에서 막힌다.
그래서 리뷰는 "어디가 왜 문제인지 학습자가 스스로 찾게 하는 질문"과 "확인할 수 있는 근거"로 구성한다.

## 절차

1. **미션 문서를 먼저 읽는다**: `phase-*/missions/M*-*.md`의 요구사항, 테스트 시나리오, 제약, 완료 기준.
2. **실행해서 확인한다**: 해당 workspace에서 `./gradlew test`를 실행하고 결과(통과/실패 개수)를 기록한다. 동시성 미션은 `--rerun-tasks`로 3회 실행해 결과가 같은지 본다.
3. **시나리오 대조**: 미션의 테스트 시나리오 번호마다 대응하는 테스트 메서드가 있는지 표로 만든다. 빠진 번호를 적는다.
4. **아래 관점으로 코드를 읽는다.**
5. **보고서 작성** (형식은 아래).

## 리뷰 관점 (우선순위 순)

| 관점 | 확인 내용 |
|---|---|
| 정합성 | 돈이 생기거나 사라지는 경로가 있는가. 예외 발생 시 상태가 일부만 바뀌는가 |
| 불변식 | 잔액 ≥ 0, 차변 = 대변 같은 규칙을 객체 내부에서 지키는가, 외부에서 깨뜨릴 수 있는가 |
| 동시성 | 공유 가변 상태가 무엇이고 무엇으로 보호하는가. check-then-act 구간이 원자적인가 |
| 테스트 품질 | 테스트 이름만 읽어도 스펙을 알 수 있는가. 기대값을 구현 코드로 만들지 않았는가. 경계값(0, 정확히 잔액, 잔액+1)이 있는가 |
| 설계 | 계층 간 의존 방향(도메인이 Spring·DB를 모르는가), 예외 계층, 이름 |
| 표현 | 매직 넘버, 중복, 메서드 길이 |

코딩테스트용 습관(`static` 필드 등)은 지적 대상이 아니다. 미션 요구사항과 위 관점에 해당하는 것만 지적한다.

## 피드백 작성 규칙

- 지적 1건 = `파일:줄` + 관찰한 사실 + 질문 1개. 예: "`Account.java:42` — 잔액 검사와 차감 사이에 다른 스레드가 끼어들 수 있다. 두 스레드가 동시에 이 줄에 도착하면 각각 어떤 잔액을 읽는가?"
- 정답 코드를 쓰지 않는다. 학습자가 3번 이상 같은 지적에서 막혔다고 말하면, API 이름이나 공식 문서 위치까지 알려준다.
- 잘한 점은 근거와 함께 1~3개 적는다(어느 줄이 어떤 규칙을 지켰는지). 다음에도 같은 방식을 쓰게 하기 위해서다.
- L3 미션의 테스트 시나리오 표 리뷰: 빠진 경계값·동시성·장애 시나리오를 "이 경우 결과가 무엇이어야 하는가?" 질문으로 제시한다.

## 보고서 형식

```markdown
## M{P}-{N} 리뷰 — {날짜}
### 실행 결과
- `./gradlew test`: 통과 {a} / 실패 {b} (3회 실행 결과 동일 여부)
### 시나리오 대응표
| 시나리오 # | 테스트 메서드 | 상태 |
### 반드시 고칠 것 (정합성·불변식·동시성)
1. `파일:줄` — 관찰 — 질문
### 고려할 것 (테스트·설계·표현)
### 잘한 점
### 다음 미션 전에 확인할 개념
- {README 절 번호 또는 self-check 항목}
```

리뷰가 끝나면 학습자가 반복해서 틀리는 유형을 `til/weakness.md`에 한 줄로 추가하도록 제안한다(파일이 없으면 만들라고 안내).
