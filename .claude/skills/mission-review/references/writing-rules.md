# 리뷰와 템플릿 작성 규칙

이 파일은 코드리뷰 보고서, 인라인 리뷰 댓글, 이슈와 PR 본문, 그 본문을 만드는 스크립트 출력에 적용한다.
검사 스크립트: `python3 .claude/skills/mission-review/scripts/check_text.py <파일들>` (규칙 위반 0건이 통과)

## 1. 문장 규칙

1. 모든 문장에는 아래 4가지 중 하나 이상이 들어간다. 하나도 없는 문장은 지운다.
   - `파일:줄`
   - 클래스, 메서드, 변수, 명령어 이름 (인라인 코드로)
   - 숫자 (금액, 개수, 시간, 시나리오 번호)
   - 물음표로 끝나는 질문
2. 평가 대신 관찰을 쓴다. "구조가 좋다"가 아니라 "`Account`의 필드 3개가 모두 `private final`이다"처럼 코드에서 확인한 사실을 쓴다.
3. 추측하지 않는다. 코드를 실행하지 않았으면 "실행하면 X가 된다"고 쓰지 않고 "42번 줄과 45번 줄 사이에 잠금이 없다"처럼 읽은 사실만 쓴다.
4. 다른 미션이나 Phase를 가리킬 때는 `docs/curriculum-map.md` 또는 Phase README에서 확인한 미션 번호와 절 번호만 쓴다.
5. 끝맺음 인사, 격려, 요약 반복, 작성 환경이나 도구 제약 설명을 쓰지 않는다.

## 2. 쓰지 않는 기호

| 기호 | 대신 쓰는 것 |
|---|---|
| `·` (가운뎃점) | 쉼표, 또는 항목을 줄로 나눈다 |
| `—` (긴 줄표) | 쉼표, 괄호, 또는 문장을 나눈다 |
| 이모지 (체크, 엑스, 경고, 원 등) | 표에서는 `충족`/`미충족`, `있음`/`없음`, `해결`/`미해결` 같은 단어 |

## 3. 쓰지 않는 표현

| 쓰지 않는 표현 | 이유 | 대신 쓰는 것 |
|---|---|---|
| 훌륭하다, 잘 작성했다, 깔끔하다, 완벽하다, 인상적이다, 우수하다, 좋은 코드 | 근거 없는 평가 | 지킨 규칙과 위치: "`Money.java:12` 문자열 생성자로 `BigDecimal`을 만든다 (M1-1 제약 2)" |
| 전반적으로, 대체로, 다소, 약간 | 범위가 없음 | 대상 파일과 개수: "테스트 22개 중 3개" |
| 적절하다, 충분하다, 효율적이다 | 기준이 없음 | 기준 수치나 규칙 |
| 가독성, 유지보수성, 확장성, 견고하다 | 측정할 수 없음 | 구체 현상: "같은 검증 코드가 `deposit`과 `withdraw`에 2번 있다" |
| 개선의 여지가 있다, 더 나은 방법이 있다 | 무엇을 바꿀지 없음 | 문제 현상과 질문 |
| 고려해 보세요, ~하는 것이 좋습니다, ~를 추천합니다, ~는 어떨까요 | 권유만 있고 근거가 없음 | 관찰 + 질문 |
| ~것 같습니다, ~것으로 보입니다 | 추측 | 확인한 사실만 쓰거나, 확인 방법을 쓴다 |
| 살펴보겠습니다, 결론적으로, 요약하자면, 중요합니다, 핵심입니다, 도움이 될 것입니다 | 내용이 없는 연결어 | 지운다 |

## 4. 예시

쓰지 않는 문장:
> 전반적으로 깔끔하게 잘 작성되었습니다! 다만 동시성 처리는 개선의 여지가 있어 보입니다.

쓰는 문장:
> `Account.java:42` 잔액 검사(`balance >= amount`)와 45번 줄 차감 사이에 잠금이 없다. 잔액 1,000원 계좌에서 스레드 2개가 800원씩 동시에 출금하면 45번 줄 실행 후 잔액은 얼마인가?
