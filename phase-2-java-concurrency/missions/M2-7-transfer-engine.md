# M2-7 [종합] 스레드 안전한 메모리 이체 엔진

## 목표
Phase 2에서 배운 모든 것을 종합해, 아래 요구사항을 만족하는 이체 엔진을 설계·구현·검증한다.
**설계 결정과 근거를 문서로 남기는 것**까지가 과제다.

## 요구사항

### 기능
- 계좌 개설, 입금, 출금, 이체, 잔액 조회, 거래내역 조회
- **1일 이체 한도**: 계좌별 하루 누적 이체 금액 5,000,000원 초과 불가 (동시 요청에도 정확히 지켜져야 함)
- **멱등성**: 같은 `requestId`로 이체 요청이 두 번 오면, 두 번째는 실제 이체 없이 첫 번째 결과를 그대로 반환
  (네트워크 재시도 시 이중 출금 방지 — 실제 금융 시스템의 핵심 요구사항)

### 비기능
- 서로 다른 계좌 간 작업은 **서로 블로킹하지 않아야** 한다 (전역 락 금지)
- 데드락 없음
- 락 획득 대기는 최대 3초, 초과 시 명확한 예외

### 인터페이스 (예시, 자유롭게 바꿔도 됨)
```java
public interface TransferEngine {
    TransferResult transfer(TransferCommand command);  // requestId, from, to, amount, memo
    Money balanceOf(AccountNumber accountNumber);
    List<Transaction> historyOf(AccountNumber accountNumber);
}
```

## 검증 테스트 (모두 작성)

| # | 시나리오 | 검증 |
|---|---|---|
| 1 | 계좌 100개(각 1,000,000원), 가상 스레드 10,000개가 랜덤 이체 | 총액 보존, 모든 잔액 ≥ 0, 데드락 없음 |
| 2 | 1번 이후 각 계좌 `Ledger.replayBalance` | `balanceOf`와 일치 |
| 3 | 한 계좌에서 1,000,000원씩 동시에 10건 이체 (한도 5,000,000) | 정확히 5건 성공, 5건 한도 초과 |
| 4 | 같은 `requestId`로 동시에 100건 요청 | 실제 이체 1건, 100건 모두 같은 결과 반환 |
| 5 | A→B, B→A 동시 대량 이체 | 데드락 없음, 총액 보존 |
| 6 | 서로 다른 계좌쌍 이체가 병렬로 처리되는지 | 한 쌍이 락을 오래 잡고 있어도 다른 쌍은 지연되지 않음 |
| 7 | 1~6을 `@RepeatedTest(100)` | 100% 통과 |

## 설계 문서 (`workspace/DESIGN.md`)
아래 질문에 답하는 1~2페이지 문서:
1. 공유 가변 상태는 무엇이고, 각각 어떻게 보호했나?
2. 락 순서는 어떻게 정했나? 같은 계좌 이체는?
3. 한도 체크와 출금이 원자적으로 일어나도록 어떻게 했나? (체크 후 출금 사이에 다른 이체가 끼어들면?)
4. 멱등성 키 저장소는 무엇을 썼나? (`ConcurrentHashMap.computeIfAbsent`? `putIfAbsent`? 처리 중인 요청은?)
5. 이 엔진의 한계는? 서버를 2대로 늘리면 무엇이 깨지나? → **이게 Phase 5~8을 배우는 이유다**
