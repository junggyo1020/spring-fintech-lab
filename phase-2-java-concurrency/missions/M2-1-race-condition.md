# M2-1 Race condition 재현

> 가이드 수준: L2 · 예상 시간: 3~4h · 선행: M1-5

## 목표
이 미션을 끝내면 다음을 할 수 있다.
- `count++`가 lost update를 일으키는 것을 테스트로 보여주고, `javap -c` 출력에서 `count++`를 이루는 바이트코드 명령어를 짚어 설명한다.
- Phase 1 `Account`에 스레드 100개가 동시에 출금할 때 잔액이 기대값과 달라지는 결과를 10회 실행 결과표로 기록한다.
- `volatile` 없는 종료 플래그 때문에 워커 스레드가 멈추지 않는 현상을, 테스트 JVM을 멈추게 하지 않는 방식으로 관찰해 기록한다.

## 배경
은행 잔액 변경은 "잔액 읽기 → 새 잔액 계산 → 잔액 쓰기" 3단계다. 두 요청이 이 3단계 사이에 끼어들면 한쪽 출금이 사라지고(lost update), 장부상 출금 합계와 잔액이 맞지 않는 사고가 된다. 이런 버그는 단위 테스트를 순차로 돌리면 한 번도 드러나지 않고, 운영 트래픽이 몰린 시점에만 나타난다. Phase 1에서 만든 `Account`와 `BankService`는 스레드 1개를 가정했다. 이 미션은 그 코드를 그대로 두고 여러 스레드에서 실행해 버그를 재현하는 데서 시작한다. 고치는 일은 M2-2부터 한다.

## 요구사항
1. **1단계 — 카운터 lost update**
   - `lab.bank.concurrency.UnsafeCounter`: `int` 필드 하나, `void increment()`(필드에 `++`), `int get()`. 동기화·`volatile`·Atomic 클래스를 쓰지 않는다.
   - 시행 1회 = 스레드 100개가 README 5절 틀로 동시에 출발해 각자 `increment()`를 10,000회 호출. 기대값 1,000,000.
   - 테스트는 시행을 최대 10회 반복하고, 10회 중 1회 이상 `get() < 1_000_000`이면 통과한다. 10회 모두 1,000,000이면 실패한다.
   - 10회 값 전부를 TIL 표에 적는다. 정확히 1,000,000이 나오는 회차도 있다 (이 문서 작성 시 macOS arm64·JDK 21.0.8에서 10회 중 1~3회). 회차마다 값이 다른 이유를 TIL에 적는다.
   - `javap -c -p`로 `UnsafeCounter.class`를 역어셈블해 `increment()`의 바이트코드 목록을 TIL에 붙이고, 읽기·계산·쓰기에 해당하는 명령어(`getfield`, `iadd`, `putfield` 등)를 표시한다.
2. **2단계 — 계좌 출금 lost update**
   - Phase 1의 `Account`를 수정 없이 사용한다. 잔액 1,000,000원 계좌 1개, 스레드 100개가 동시에 `withdraw(Money.won(10_000))`을 1회씩 호출한다.
   - 순차 실행 기준 기대 결과: 성공 100건, 실패 0건, 최종 잔액 0원.
   - 이 시나리오를 10회 실행하고, 회차별 `성공 건수`, `실패 건수`, `최종 잔액`, `성공 건수 × 10,000 + 최종 잔액`(1,000,000이 아니면 lost update)을 표로 기록한다.
   - 10회 모두 기대 결과와 같으면 경쟁 구간을 넓힌다. `Account`의 잔액 읽기와 쓰기 사이에 테스트에서만 동작하는 지연(`Thread.sleep(1)` 또는 `Thread.yield()`)을 넣는 방법을 직접 설계한다. 운영 코드 경로에서는 지연이 0이어야 한다. 넣은 방법과 넣은 뒤 10회 결과를 따로 기록한다.
3. **3단계 — 가시성**
   - 아래 `Worker`를 테스트 코드 안에 만든다.
     ```java
     class Worker implements Runnable {
         private boolean stopped = false;      // volatile 없음
         void stop() { stopped = true; }
         public void run() { long n = 0; while (!stopped) { n++; } }
     }
     ```
   - 워커 스레드는 `setDaemon(true)`로 만든다. 데몬 스레드는 JVM 종료를 막지 않으므로, 루프가 끝나지 않아도 테스트 JVM이 종료된다.
   - 순서: 워커 시작 → 메인 스레드 1초 대기 → `stop()` 호출 → `join(3_000)`(최대 3초 대기) → `isAlive()` 값을 기록.
   - `stopped`에 `volatile`을 붙인 버전도 같은 순서로 실행해 `isAlive()`를 기록한다. 두 버전을 각각 5회 실행한 결과를 표로 남긴다.
   - 이 테스트는 결과를 단정(assert)하지 않고 출력만 한다. 결과는 JIT 컴파일 여부에 따라 실행마다, JVM마다 다를 수 있다 (이 문서 작성 시 JDK 21.0.8에서 `volatile` 없는 버전은 3회 모두 `isAlive() == true`).

## 테스트 시나리오

| # | 준비(Given) | 실행(When) | 기대 결과(Then) |
|---|---|---|---|
| 1 | `UnsafeCounter` 새 객체, 스레드 100개 | 각 스레드가 `increment()` 10,000회, 이 시행을 최대 10회 | 10회 중 1회 이상 `get() < 1,000,000` |
| 2 | `Account` 잔액 1,000,000원, 스레드 100개 | 동시에 `withdraw(10,000원)` 1회씩 | 출력만 함. TIL 표에 성공 건수·실패 건수·최종 잔액 기록 |
| 3 | 2와 같음 + 읽기·쓰기 사이 테스트용 지연 | 동시에 `withdraw(10,000원)` 1회씩, 10회 | 10회 중 1회 이상 `성공 건수 × 10,000 + 최종 잔액 > 1,000,000` |
| 4 | `Worker`(`volatile` 없음), 데몬 스레드 | 1초 후 `stop()`, `join(3_000)` | 출력만 함. `isAlive()` 값 기록 (`true`가 나올 수 있다) |
| 5 | `Worker`(`stopped`가 `volatile`), 데몬 스레드 | 1초 후 `stop()`, `join(3_000)` | `isAlive() == false` |

시나리오 3의 계산: 출금이 성공할 때마다 잔액이 10,000원씩 줄어야 하므로 `성공 건수 × 10,000 + 최종 잔액 == 1,000,000`이 정상이다. lost update가 생기면 성공으로 집계된 출금 일부가 잔액에 반영되지 않아 합이 1,000,000보다 커진다.

## 제약
- 이 미션에서는 버그를 고치지 않는다. `synchronized`, `volatile`(3단계 비교 버전 제외), `java.util.concurrent.atomic`를 쓰지 않는다.
- 3단계 워커는 반드시 데몬 스레드로 만든다. 일반 스레드로 만들면 루프가 끝나지 않을 때 Gradle 테스트 프로세스가 끝나지 않는다.
- 테스트용 지연은 운영 코드에서 기본값 0(지연 없음)이어야 한다.
- `InterruptedException`을 잡으면 `Thread.currentThread().interrupt()`로 플래그를 복구한다 (README 5절).

## 힌트
<details>
<summary>힌트 1: 1단계에서 회차마다 결과가 다른 이유</summary>

같은 JVM에서 시행을 반복하면 뒤 회차일수록 `increment()`가 JIT 컴파일된 코드로 실행된다. 스레드 1개가 10,000회를 처리하는 데 걸리는 시간이 다른 스레드의 시작 시간 차이보다 짧아지면, 스레드들이 겹쳐 실행되는 구간이 줄어든다. `-Xint`(인터프리터만 사용) 옵션으로 실행하면 결과가 어떻게 바뀌는지 비교해 본다.
</details>

<details>
<summary>힌트 2: 3단계에서 루프가 끝나지 않는 이유</summary>

JIT는 루프 안에서 `stopped`를 쓰는 코드가 없으면 `stopped` 읽기를 루프 밖으로 꺼낼 수 있다 (hoisting). JLS 17.4의 happens-before 관계가 없는 쓰기는 다른 스레드에 보인다는 보장이 없다. 루프 안에 `System.out.println`을 넣으면 재현이 안 될 수 있는데, `PrintStream.println` 구현 안에 무엇이 있는지 JDK 소스에서 확인한다.
</details>
