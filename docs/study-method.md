# 학습 방법

## 원칙

1. **직접 타이핑한다.** 복사-붙여넣기 금지. 미션 문서의 예시 코드도 손으로 친다.
2. **테스트가 먼저다.** "동작한다"는 테스트가 증명한다. 눈으로 확인한 건 확인한 게 아니다.
3. **재현 → 설명 → 해결 → 증명.** 특히 동시성 문제는 반드시 이 4단계를 거친다.
4. **왜?를 3번 묻는다.** "락을 건다 → 왜? → 동시에 수정되니까 → 왜 문제? → lost update → 왜 생기지? → read-modify-write가 원자적이지 않아서"
5. **막히면 30분 룰.** 30분 혼자 고민 → 힌트 열기 → 30분 더 → 질문/리뷰 요청.

## 하루 루틴 (2시간 기준)

| 시간 | 할 일 |
|---|---|
| 0:00–0:10 | 어제 TIL 다시 읽기 |
| 0:10–0:40 | 개념 학습 (Phase README, 공식 문서, 책) |
| 0:40–1:40 | 미션 코딩 (테스트 → 구현 → 리팩터링) |
| 1:40–2:00 | TIL 작성 + 커밋 |

## 브랜치 & 커밋 규칙

```
main                       ← 리뷰 끝난 코드만
└── phase1/m1-1-money      ← 미션별 브랜치
```

커밋 메시지 (Conventional Commits):

```
test: Money 덧셈 테스트 추가
feat: Money 덧셈 구현
refactor: Money 생성 검증 로직 분리
docs: M1-1 TIL 작성
```

- 테스트 커밋과 구현 커밋을 **분리**해보자. 나중에 히스토리를 보면 TDD 흐름이 보인다.

## TIL 작성법

`til/YYYY-MM-DD-주제.md` 형식. 템플릿은 [til/TEMPLATE.md](../til/TEMPLATE.md).

좋은 TIL = "무엇을 했다"가 아니라 **"무엇을 몰랐고, 이제 무엇을 알게 되었는지"**.

## 리뷰 받는 법

미션 하나를 끝내면 Claude Code 세션에서 다음처럼 요청한다:

```
phase1/m1-1-money 브랜치의 M1-1 과제 코드 리뷰해줘.
정답 코드는 주지 말고, 문제점과 개선 방향을 질문 형태로 알려줘.
```

리뷰 관점 체크리스트:
- [ ] 미션의 요구사항과 검증 기준을 모두 만족하는가
- [ ] 테스트 이름만 읽어도 스펙이 이해되는가
- [ ] 불변식(invariant)이 객체 내부에서 지켜지는가 (외부에서 깨뜨릴 수 없는가)
- [ ] 예외 메시지가 디버깅에 도움이 되는가
- [ ] 동시성 관련: 공유 가변 상태가 어디에 있는가, 어떻게 보호되는가
