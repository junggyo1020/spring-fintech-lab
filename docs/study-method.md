# 학습 방법

## 원칙

1. **직접 타이핑한다.** 미션 문서의 코드 조각(테스트 틀, 설정 파일)도 복사, 붙여넣기 하지 않고 손으로 친다. 설정 파일은 예외로 붙여넣어도 되지만, 붙여넣은 줄마다 무슨 역할인지 TIL에 한 줄씩 적는다.
2. **테스트가 먼저다.** 테스트가 실패하는 것을 먼저 확인하고(컴파일 실패 포함) 구현한다. 콘솔에 찍어서 눈으로 확인한 것은 완료 기준으로 인정하지 않는다.
3. **재현 → 원인 설명 → 해결 → 증명.** 동시성, 트랜잭션 문제는 반드시 이 4단계를 거친다. "해결"은 재현 테스트가 통과로 바뀌는 것으로 증명한다.
4. **"왜?"를 3번 묻는다.** 예: "락을 건다 → 왜? 동시에 수정되니까 → 왜 문제? lost update가 생기니까 → 왜 생기지? 읽기-계산-쓰기가 원자적이지 않아서".
5. **막히면 30분 규칙.** 혼자 30분 → 미션의 힌트 열기 → 30분 더 → 리뷰나 질문 요청. 질문할 때는 "시도한 것, 기대한 결과, 실제 결과(에러 메시지 원문)"를 함께 적는다.

## 주간 시간 배분 (주 13시간 예시)

| 요일 | 시간 | 할 일 |
|---|---|---|
| 월~금 | 2시간씩 (총 10시간) | 아래 하루 루틴 |
| 토 또는 일 | 3시간 | 이번 주 미션 마무리, PR 리뷰 반영, 이번 주 TIL을 다시 읽고 self-check 해당 항목 답해보기 |

## 하루 루틴 (2시간)

| 시간 | 할 일 |
|---|---|
| 0:00–0:10 | 어제 TIL과 `til/weakness.md` 다시 읽기 |
| 0:10–0:40 | 개념 학습: Phase README의 핵심 개념 절, 미션의 읽을거리 |
| 0:40–1:40 | 미션 코딩: 테스트 작성 → 실패 확인 → 구현 → 리팩터링 |
| 1:40–2:00 | TIL 작성 + 커밋 + push |

## 가이드 수준별 진행 방법

| 수준 | 진행 방법 |
|---|---|
| L1 (Phase 0~1) | 테스트 시나리오 표의 행 하나를 테스트 메서드 하나로 옮긴다. 미션 번호와 표의 `#` 번호를 `@DisplayName`에 넣는다 (예: `@DisplayName("M1-1 #3 통화가 다르면 더할 수 없다")`) |
| L2 (Phase 2~5) | 시그니처가 없는 클래스는 필드와 메서드를 먼저 종이나 주석으로 설계한 뒤 테스트를 쓴다. 측정 미션은 표의 열 이름을 그대로 쓴다 |
| L3 (Phase 6~8) | 구현 전에 "직접 작성할 테스트 시나리오" 표를 `workspace/docs/test-scenarios/M{P}-{N}.md`로 만들어 리뷰를 받는다. 미션의 "반드시 포함할 경우"가 모두 들어가야 구현으로 넘어간다 |

## 브랜치 & 커밋 규칙

```
main                       ← 리뷰가 끝난 코드만
└── phase1/m1-1-money      ← 미션별 브랜치
```

커밋 메시지 형식: `[type] 한글 설명` (type은 소문자, 끝에 마침표 없음)

```
[test] Money 덧셈 테스트 추가
[feat] Money 덧셈 구현
[refactor] Money 생성 검증 로직 분리
[docs] M1-1 TIL 작성
```

- 테스트 커밋과 구현 커밋을 나눈다. 히스토리에서 "실패하는 테스트 → 구현" 순서가 보이게 하기 위해서다.
- M0-3 이후로는 PR마다 GitHub Actions CI가 `./gradlew test`를 실행한다. CI가 실패한 PR은 머지하지 않는다.

## TIL 작성법

- 파일: `til/YYYY-MM-DD-주제.md`, 템플릿: [til/TEMPLATE.md](../til/TEMPLATE.md)
- "무엇을 했다"가 아니라 **"무엇을 몰랐고, 지금은 무엇을 설명할 수 있는가"**를 쓴다.
- 같은 실수를 두 번 하면 `til/weakness.md`에 한 줄 추가한다: `날짜 | 미션 | 틀린 내용 | 올바른 내용`.

## 미션 진행 흐름 (이슈, PR, 리뷰, 머지)

미션 1개는 GitHub에서 아래 순서로 진행한다. 상세 절차와 스크립트 옵션은 `.claude/skills/study-workflow/SKILL.md`에 있다.

| 단계 | 하는 일 | 명령 또는 요청 |
|---|---|---|
| 1. 이슈 | 미션 문서에서 이슈를 만든다. 이슈의 진행 체크리스트를 체크하면 진행률이 표시된다 | `python3 .claude/skills/study-workflow/scripts/mission_issue.py M1-1` |
| 2. 실습 | 이슈 본문의 브랜치 이름으로 브랜치를 만들고 `[test]` 커밋, 구현 커밋 순서로 커밋한다 | `git switch -c phase1/m1-1-money` |
| 3. 질문 | 30분 넘게 막히면 "질문" 템플릿으로 이슈를 만들고 댓글에 `@claude`를 쓴다 | GitHub 이슈 > New issue > 질문 |
| 4. PR | 학습자 메모 5개 절(구현 요약, 설계 결정과 이유, 리뷰어에게 묻고 싶은 것, 실제 소요 시간, TIL)을 쓰고 PR을 만든다 | Claude Code에서 "M1-1 PR 올려줘" |
| 5. 리뷰 | Claude(미션 문서 기준, 판정 포함)와 Gemini Code Assist(줄 단위 코드 결함)가 리뷰를 단다 | 자동 |
| 6. 반영 | 지적 1건마다 커밋하고 PR 본문 "리뷰 반영 기록" 표에 줄을 추가한 뒤 재리뷰를 요청한다 | PR 댓글에 `@claude 다시 리뷰`, `/gemini review` |
| 7. 머지 | Claude 리뷰 판정이 "머지 가능"이면 머지한다 | `gh pr merge <번호> --merge --delete-branch` |

PR 본문의 "자동 점검 결과"(테스트 개수, 시나리오 대응, 커밋 순서, 금지 패턴, 변경 파일)는 스크립트가 채운다. 시나리오 대응은 `@DisplayName`에서 `"M1-1 #3"`처럼 미션 번호와 시나리오 번호가 붙은 부분을 찾는다. 한 Phase의 workspace에 여러 미션의 테스트가 함께 있어서 미션 번호가 없으면 다른 미션의 3번과 구분되지 않는다.

## 리뷰 받는 법

PR을 올리면 리뷰가 자동으로 달린다. PR 없이 로컬에서 먼저 보려면 Claude Code 세션에서 요청한다. 두 경우 모두 `.claude/skills/mission-review/SKILL.md` 기준을 쓴다.

```
phase1/m1-1-money 브랜치의 M1-1 과제 코드 리뷰해줘.
```

지적 1건은 `파일:줄`, 관찰, 확인 방법, 질문으로 온다. 등급은 필수(머지 전에 고친다), 권장(최대 5건), 질문(설명이 필요한 부분) 3가지다.
확인 방법에 적힌 테스트를 직접 만들어 실행하고, 질문에 답을 찾은 뒤 고친다. 같은 지적이 다음 리뷰에서도 미해결이면 README 절 번호, 그다음에는 API 이름이 힌트로 추가된다.

L3 미션은 구현 전에 시나리오 표만 Draft PR로 올리고 PR 댓글에 `@claude 시나리오 표 리뷰`를 쓴다. 로컬에서는 이렇게 요청한다.

```
M6-3 테스트 시나리오 표 검토해줘. (phase-6-core-banking/workspace/docs/test-scenarios/M6-3.md)
```

스스로 확인할 체크리스트:
- [ ] 미션의 완료 기준 체크박스를 모두 확인했다
- [ ] 테스트 이름(`@DisplayName`)만 읽어도 스펙이 보인다
- [ ] 불변식(잔액 ≥ 0 등)이 객체 내부에서 지켜지고, 외부 코드로 깨뜨릴 수 없다
- [ ] 예외 메시지에 원인 파악에 필요한 값(계좌번호는 마스킹, 요청 금액, 현재 상태)이 있다
- [ ] 공유 가변 상태가 어디에 있고 무엇으로 보호되는지 말할 수 있다
